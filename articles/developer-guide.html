Developer Guide

Use this page when you are returning to the repository and need the shortest reliable path back into development.

Daily Loop

  1. Read the active spec under spec/features/ before changing behavior.
  2. Start local dependencies.
  3. Run the API and portal with HTTPS launch profiles.
  4. Make the smallest scoped change that matches the spec.
  5. Run targeted tests first, then a solution build before committing.
  6. Update conceptual docs when behavior changes.

Local Startup

From the repository root:

Copy-Item .\.env.example .\.env
docker compose --env-file .\.env up -d
pwsh ./scripts/bootstrap-keycloak-provisioner.ps1 -SkipCertificateCheck
dotnet run --project .\Code7Dev.Organizor.Api\Code7Dev.Organizor.Api.csproj --launch-profile https
dotnet run --project .\Code7Dev.Organizor.Portal.Ui\Code7Dev.Organizor.Portal.Ui.csproj --launch-profile https

On a fresh Keycloak database, Docker Compose imports the platform realm and the bootstrap script creates the backend-only master-realm organizor-provisioner service account. The script is safe to rerun and smoke-verifies its Keycloak Admin REST access without printing secrets. See Local Development before using it with a reset environment.

Expected local URLs:

Component URL
Portal UI https://localhost:7025
API https://localhost:7184
API HTTP fallback http://localhost:5100
Keycloak https://localhost:8443
Scalar https://localhost:7184/scalar

For certificate setup, reset steps, and troubleshooting, use Local Development.

Verification Commands

Use these commands from the repository root:

dotnet build .\Code7Dev.Organizor.Api.slnx --no-restore -p:OutDir=C:\tmp\organizor-build\out\
dotnet test .\Code7Dev.Organizor.Tests\Code7Dev.Organizor.Tests.csproj --no-build -p:OutDir=C:\tmp\organizor-build\out\
git diff --check

For a clean build without relying on a previous restore:

dotnet build .\Code7Dev.Organizor.Api.slnx -p:OutDir=C:\tmp\organizor-build\out\

If the normal build output is locked by a running API or debugger, keep using the temporary OutDir pattern above.

Tenant-Scoped API Calls

Tenant-scoped API requests require both:

  • Authorization: Bearer <token>
  • X-Tenant-Slug: <tenant-slug>

Tenant-specific clients supply their known tenant slug from their own runtime configuration or public auth contract. The API requires the token issuer to match the catalog realm for that header; a tenant token claim is compatibility data, not tenant authorization. Platform control-plane routes select tenants by catalog identifier and use a platform organizor-admin token. Anonymous public registration does not use the authenticated handler; it sends the tenant slug in the public registration request body.
