API Integration — Portal UI

The Portal UI communicates with the Organizor API through named HTTP clients. Authenticated backend calls use the api client. Anonymous public registration uses the public-api client without the authorization message handler.

Local Development Configuration

Setting Value
Portal origin https://localhost:7025
API base URL https://localhost:7184
Authorized API URL https://localhost:7184
Token issuer https://localhost:8443/realms/organizor-dev
Portal OIDC client organizor-ui

The portal and API must agree on the Keycloak issuer. If the portal logs in through HTTPS but the API validates against the old HTTP authority, API requests fail with 401 Unauthorized.

HttpClient Registration

The portal registers the API client in Program.cs:

builder.Services.AddHttpClient("api", client =>
{
    client.BaseAddress = new Uri("https://localhost:7184");
})
.AddHttpMessageHandler<ApiAuthorizationMessageHandler>();

AdminTenantService, TenantUserService, and TenantConfigService use IHttpClientFactory.CreateClient("api") to call authenticated API endpoints.

Authorization Handler

ApiAuthorizationMessageHandler extends Blazor's AuthorizationMessageHandler. It is responsible for:

  • configuring the authorized API URL;
  • requesting the portal OIDC scopes;
  • attaching the access token to outgoing API requests;
  • adding the X-Tenant-Slug header when a tenant claim is available.

The handler is registered in DI and configured once in its constructor. This matters because AuthorizationMessageHandler.ConfigureHandler(...) can only be called once per handler instance. Calling ConfigureHandler(...) again for the same handler instance can cause this runtime error:

handler already configured

Keep handler configuration inside the handler constructor or inside the AddHttpMessageHandler factory, but not both. The current branch uses the constructor approach.

Tenant Admin API Client

AdminTenantService wraps the admin tenant API surface used by /admin/tenants and /admin/plans. Tenant query, lifecycle, effective config, override, and plan-management endpoints require the Organizor admin policy.

Method Endpoint Purpose
GetTenantsAsync GET /api/admin/tenants Loads all tenants, including soft-deleted records.
OnboardAsync POST /api/admin/tenants/onboard Creates the catalog tenant, provisions Keycloak resources, creates the database, and applies migrations.
UpgradeAsync POST /api/admin/tenants/{id}/upgrade Runs pending migrations for the tenant database.
SoftDeleteAsync DELETE /api/admin/tenants/{id} Marks a tenant as deleted without dropping the database.
HardDeleteAsync POST /api/admin/tenants/{id}/hard-delete Drops the tenant database and removes the catalog record after soft deletion.
GetConfigAsync GET /api/admin/tenants/{id}/config Loads the tenant's effective config after plan defaults and overrides are resolved.
GetConfigOverridesAsync GET /api/admin/tenants/{id}/config-overrides Loads explicit tenant-level config overrides.
UpdateConfigOverridesAsync PUT /api/admin/tenants/{id}/config-overrides Updates tenant-level config overrides.
GetPlansAsync GET /api/admin/tenant-plans Loads tenant plan defaults.
UpdatePlanAsync PUT /api/admin/tenant-plans/{planKey} Updates tenant plan defaults.
tenant user methods /api/admin/tenants/{tenantId}/users/* Manage users for a selected tenant from the platform control plane.

The backend also exposes GET /api/admin/tenants/{id} for admin detail lookups. The current portal grid does not call that endpoint directly.

All methods expect an authenticated organizor-admin user. 401 Unauthorized means the token is missing or invalid. 403 Forbidden means the token is valid but lacks the required role.

Tenant query responses include lifecycle fields that the portal relies on:

{
  "id": "11111111-1111-1111-1111-111111111111",
  "name": "Acme",
  "slug": "acme",
  "databaseName": "organizor_tenant_acme",
  "createdAt": "2026-06-09T10:30:00Z",
  "status": "Active",
  "failureReason": null,
  "isDeleted": false
}

GET /api/v1/tenants returns only non-deleted catalog records. GET /api/admin/tenants intentionally includes soft-deleted records so the portal can show deleted tenants and allow hard deletion.

Tenant User API Client

TenantUserService wraps tenant-scoped user-management endpoints used by /tenant/users.

These requests require a bearer token with tenant-admin and the X-Tenant-Slug header. ApiAuthorizationMessageHandler adds the tenant header when the authenticated user has a tenant claim.

Tenant admins can create users, list users, toggle enabled state, assign tenant roles, and delete users inside their own tenant. Regular tenant-user accounts do not get this portal route.

Tenant Config API Client

TenantConfigService wraps the tenant-scoped config endpoint used by tenant admins at /tenant/config.

Method Endpoint Purpose
GetConfigAsync GET /api/v1/tenant/config Loads the current tenant's effective config.

The request must include a bearer token with tenant-admin and the X-Tenant-Slug header. ApiAuthorizationMessageHandler adds the tenant header when the authenticated user has a tenant claim.

Static Tenant Website API Contract

Tenant-specific static websites should first call:

GET /api/public/tenants/{slug}/auth

The response contains the tenant's website base URL, public Keycloak authority, generated client id, PKCE requirement, scopes, redirect metadata, tenant header name, tenant claim name, expected tenant roles, expected tenant group paths, and public registration endpoint. This endpoint intentionally returns no secrets.

After login, static tenant websites must send Authorization: Bearer <token> and X-Tenant-Slug: {slug} on tenant-scoped authenticated API calls.

Public Registration API Client

PublicRegistrationService wraps POST /api/public/register for the temporary /register shell. It uses the named public-api client instead of the authenticated api client because registration is anonymous and the tenant slug is supplied in the request body.

The future tenant-specific static websites should reuse the same public registration contract with their own UI.

Error Handling

The tenant API client uses EnsureSuccessAsync to surface failed API responses as InvalidOperationException. The exception message includes the status code and response body when present. The Radzen tenant page catches those exceptions and displays both a page alert and a Radzen notification.

Troubleshooting

Symptom Likely cause Fix
handler already configured The same AuthorizationMessageHandler instance was configured more than once. Configure the handler in one place only. The current branch configures it in ApiAuthorizationMessageHandler's constructor.
401 Unauthorized while logged in API Keycloak:Authority does not match the token issuer, or no access token was attached. Align API authority with https://localhost:8443/realms/organizor-dev and verify the named API client uses the auth handler.
403 Forbidden while logged in The token is valid but does not include organizor-admin. Assign the role in Keycloak and log in again to get a fresh token.
Tenant-scoped API returns bad tenant errors Tenant header is missing or invalid. Verify the user has a tenant claim and ApiAuthorizationMessageHandler adds the header for tenant-scoped endpoints.
