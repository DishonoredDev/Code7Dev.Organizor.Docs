API Integration — Platform Portal And Tenant Clients

The Blazor portal communicates with the Organizor API through named HTTP clients. The central portal is an Organizor-admin control plane; tenant websites and tenant-admin portal hosts are separate clients with their own Keycloak realm configuration.

Local Development Configuration

Setting Value
Portal origin https://localhost:7025
TVDK tenant-admin portal origin https://localhost:7022
API base URL https://localhost:7184
Authorized API URL https://localhost:7184
Platform token issuer https://localhost:8443/realms/organizor-dev
Platform portal OIDC client organizor-ui

The API derives trusted issuers from Keycloak:BaseUrl, Keycloak:PlatformRealm, and active catalog tenant realms. It accepts platform portal tokens from the platform issuer and tenant tokens only from the realm mapped to the selected tenant. HTTPS and HTTP Keycloak endpoints are different issuers; using a different scheme causes 401 Unauthorized.

HttpClient Registration

The portal registers the authenticated API client in Program.cs:

builder.Services.AddHttpClient("api", client =>
{
    client.BaseAddress = new Uri("https://localhost:7184");
})
.AddHttpMessageHandler<ApiAuthorizationMessageHandler>();

AdminTenantService uses IHttpClientFactory.CreateClient("api") to call platform-control-plane endpoints. Anonymous public registration uses the separate public-api client without the authorization message handler.

Authorization Handler

ApiAuthorizationMessageHandler extends Blazor's AuthorizationMessageHandler. It is responsible for:

  • configuring the authorized API URL;
  • requesting portal OIDC scopes;
  • attaching the platform access token to outgoing requests.

The handler is registered in DI and configured once in its constructor. This matters because AuthorizationMessageHandler.ConfigureHandler(...) can only be called once per handler instance. Calling ConfigureHandler(...) again for the same handler instance can cause this runtime error:

handler already configured

Keep handler configuration inside the handler constructor or inside the AddHttpMessageHandler factory, but not both. The current branch uses the constructor approach.

The platform portal does not derive a tenant boundary from a tenant claim. Platform administration routes select a tenant by catalog id in their path. A tenant-specific client must send X-Tenant-Slug only for its own known tenant environment; the API still verifies that header against the token issuer.

Tenant boundary: the tenant claim is compatibility data only and is never an authorization boundary. The API binds a tenant-scoped request to the catalog-owned realm for the supplied tenant header.

Platform Tenant API Client

AdminTenantService wraps the admin tenant API surface used by /admin/tenants and /admin/plans. All of these endpoints require a platform-realm organizor-admin token.

Method Endpoint Purpose
GetTenantsAsync GET /api/admin/tenants Loads all tenants, including soft-deleted records.
OnboardAsync POST /api/admin/tenants/onboard Creates the catalog tenant, provisions its Keycloak realm, creates the database, and applies migrations.
UpgradeAsync POST /api/admin/tenants/{id}/upgrade Runs pending migrations for the tenant database.
SoftDeleteAsync DELETE /api/admin/tenants/{id} Disables the tenant realm, then marks the tenant deleted without dropping the database.
HardDeleteAsync POST /api/admin/tenants/{id}/hard-delete Deletes the complete tenant realm, then drops the database and catalog record after soft deletion.
GetConfigAsync GET /api/admin/tenants/{id}/config Loads the tenant's effective config after plan defaults and overrides are resolved.
GetConfigOverridesAsync GET /api/admin/tenants/{id}/config-overrides Loads explicit tenant-level config overrides.
UpdateConfigOverridesAsync PUT /api/admin/tenants/{id}/config-overrides Updates tenant-level config overrides.
GetPlansAsync GET /api/admin/tenant-plans Loads tenant plan defaults.
UpdatePlanAsync PUT /api/admin/tenant-plans/{planKey} Updates tenant plan defaults.
tenant user methods /api/admin/tenants/{tenantId}/users/* Manages users inside the selected tenant realm from the platform control plane.

The backend also exposes GET /api/admin/tenants/{id} for admin detail lookups. The current portal grid does not call that endpoint directly.

401 Unauthorized means the token is missing, invalid, from an untrusted issuer, or lacks the organizor-api audience. 403 Forbidden means the token is valid but lacks the platform-realm organizor-admin role.

GET /api/v1/tenants is a platform-only catalog read and returns only non-deleted records. GET /api/admin/tenants intentionally includes soft-deleted records so the portal can show deleted tenants and allow hard deletion. Tenant-realm identities cannot use either route to discover or enumerate other tenants.

Tenant-Scoped API Clients

Tenant user-management, tenant configuration, activity, people, and registration APIs are tenant-scoped. A caller needs:

  • a token from that tenant's catalog-owned realm;
  • the required realm-local role (tenant-admin or tenant-user);
  • X-Tenant-Slug for the matching tenant where the route requires a header.

For example, a tenant-pjsabbe token with X-Tenant-Slug: tvdk is rejected with 403 Forbidden. A platform-realm organizor-admin is the explicit centralized-support exception where the endpoint policy permits it.

The central Blazor portal is not a tenant-realm OIDC client. A tenant-admin uses the same Portal codebase at their tenant's configured host, which resolves a realm-local portal client before OIDC begins. The API message handler sends X-Tenant-Slug for tenant-scoped paths after login; the API then verifies it against the token issuer.

Tenant self-service account-action endpoints act only on the caller's own identity in the matching tenant realm. A platform administrator manages another tenant user through /api/admin/tenants/{tenantId}/users, never through that user's self-service account-action route.

Static Tenant Website API Contract

Tenant-specific websites must first call:

GET /api/public/tenants/{slug}/auth

The response contains the tenant's own Keycloak authority, generated client id, PKCE requirement, scopes, redirect metadata, tenant header name, tenant claim name, expected tenant roles, realm-local group paths, and public registration endpoint. This endpoint intentionally returns no secrets. A tenant website fetches it during startup, before registering its OIDC client; it must not use the central portal's organizor-dev authority or organizor-ui client as a fallback.

After login, a tenant website sends Authorization: Bearer <token> and X-Tenant-Slug: {slug} on tenant-scoped authenticated API calls. It must use the authority returned by the contract rather than hard-coding the platform realm. Before starting login, it should also verify that its own callback URL, logout URL, and browser origin occur in the returned allow-lists; a mismatch means the tenant needs corrected onboarding/auth settings.

Tenant Admin Portal Runtime Contract

At any Portal host other than Portal:PlatformBaseUrl, the browser starts by calling:

GET /api/public/tenant-portals/auth?baseUrl={url-encoded-current-base-url}

The anonymous response contains the resolved tenant slug, tenant realm authority, separate tenant-{slug}-portal client id, tenant website base URL, PKCE/scopes, and exact login/logout/origin values. It contains no client secret or Keycloak administration details. The Portal must reject a mismatch rather than falling back to the platform client.

Public Registration API Client

PublicRegistrationService wraps POST /api/public/register for the temporary /register shell. It uses the named public-api client instead of the authenticated api client because registration is anonymous and the tenant slug is supplied in the request body.

The future tenant-specific static websites should reuse the same public registration contract with their own UI.

Anonymous public form endpoints are rate limited by endpoint, tenant, and client address. A limited request returns 429 Too Many Requests with error code PUBLIC_FORM_RATE_LIMITED. Local development limits can be configured with dotnet user-secrets under:

  • PublicFormRateLimit:ActivityRegistration:PermitLimit
  • PublicFormRateLimit:ActivityRegistration:WindowMinutes
  • PublicFormRateLimit:TenantUserRegistration:PermitLimit
  • PublicFormRateLimit:TenantUserRegistration:WindowMinutes

Error Handling

The tenant API client uses EnsureSuccessAsync to surface failed API responses as InvalidOperationException. The exception message includes the status code and response body when present. The Radzen tenant page catches those exceptions and displays both a page alert and a Radzen notification.

Troubleshooting

Symptom Likely cause Fix
handler already configured The same AuthorizationMessageHandler instance was configured more than once. Configure the handler in one place only. The current branch configures it in ApiAuthorizationMessageHandler's constructor.
401 Unauthorized while logged in Token issuer is not the configured platform realm or an active catalog tenant realm, its audience is wrong, or no token was attached. Align Keycloak:BaseUrl with the token issuer's HTTPS base URL, verify the correct realm client, and request an organizor-api audience token.
403 Forbidden while logged in The token has the wrong issuer/tenant pairing or lacks the issuer-appropriate role. Use a platform organizor-admin token for platform routes, or a matching tenant realm token for tenant routes.
Tenant-scoped API returns bad tenant errors Tenant header is missing or invalid. Send the tenant's known slug in X-Tenant-Slug; do not rely on a tenant claim as proof of access.
