Spec-Driven Development

Organizor uses Spec-Driven Development for feature work. Accepted behavior is stored in repository specifications under spec/ so requirements, implementation, tests, and documentation are versioned with the code.

Constitution

Before feature work starts, read:

  • brief.md
  • tech-design.md
  • roadmap.md
  • rules.md
  • workflow.md
  • AGENTS.md
  • the relevant feature files under spec/features/

These files define customer intent, architecture boundaries, implementation constraints, feature order, standing rules, workflow, and agent behavior.

Feature Specs

Each feature lives in spec/features/{feature-slug}/ and contains:

File Purpose
specification.md Defines behavior, scope, authorization, tenancy, persistence, API impact, acceptance criteria, and open questions.
implementation.md Maps the spec to projects, layers, migrations, and rollback considerations.
testing.md Defines automated and manual verification.
documentation.md Defines DocFX, README, operator, and integration documentation updates.
finalise.md Records completion checklist, verification results, residual risk, and follow-up work.

Use spec/_templates/feature/ when starting a feature.

Feature Discovery And Health

New and newly touched feature specifications add a lightweight discovery block directly below Status:

Status: accepted
Delivery: not-started
Area: portal
Tags: tenant-admin, registration
Next Action: Implement the queue/detail review UI.
Depends On: tenant-registration-management

Legacy specifications without this block remain valid. The repository tool derives their delivery state from the existing specification, implementation, and finalise status files.

After reading the constitution, use the discovery command to find the smallest relevant specification set:

pwsh ./scripts/spec.ps1 catalog
pwsh ./scripts/spec.ps1 next
pwsh ./scripts/spec.ps1 find registration
pwsh ./scripts/spec.ps1 area portal

next lists buildable candidates; it does not replace roadmap ordering. After changing feature status or discovery metadata, refresh and validate the generated feature index:

pwsh ./scripts/spec.ps1 sync
pwsh ./scripts/spec.ps1 health

The generated catalog in spec/README.md must not be hand-edited. GitHub Actions runs the same health command for SDD-relevant pull requests and default-branch pushes.

GitHub

GitHub issues and projects are useful for discussion, prioritization, and traceability. They do not replace repository specs.

Pull requests should link the relevant feature spec and confirm that:

  • code matches the accepted specification;
  • tenant isolation was reviewed;
  • authorization was reviewed;
  • catalog and tenant database impact was reviewed;
  • DocFX documentation was updated or marked not applicable;
  • generated API reference files were not manually edited.

Before a local commit is created, the agent should summarize the changed files or feature areas, verification performed, checks not run, and proposed commit message. The commit should wait for explicit approval.

Engineering Standards

Feature implementation must follow rules.md, including the repository's C#/.NET architecture and coding standards. Apply SOLID principles pragmatically: keep services cohesive, preserve dependency direction, expose clear contracts at layer boundaries, and avoid abstractions that do not protect a real boundary or improve testability.

Drift Handling

When code and spec disagree, update the spec first or stop for a decision. Do not silently implement behavior that is missing from the spec.
