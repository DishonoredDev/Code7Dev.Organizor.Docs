Configuration

Organizor reads standard ASP.NET Core configuration from appsettings.json, environment-specific files, user secrets, and environment variables.

Catalog Connection String

CatalogDbContext expects a connection string named Catalog.

Example shape:

{
  "ConnectionStrings": {
    "Catalog": "Host=localhost;Port=5432;Database=organizor_catalog;Username=postgres;Password=<postgres-password>"
  }
}

Tenant PostgreSQL Settings

ConnectionStringBuilder builds tenant and admin connection strings from the Postgres section.

{
  "Postgres": {
    "Host": "localhost",
    "Port": "5432",
    "User": "postgres",
    "Password": "<postgres-password>"
  }
}

The admin connection uses the postgres database. Tenant connections use the tenant database name stored in the catalog.

Keycloak

The API uses one Keycloak deployment but does not use one application realm for every tenant:

  • Keycloak:PlatformRealm identifies the Organizor control-plane realm. Local development uses organizor-dev.
  • Every active catalog tenant has its own immutable Tenant.IdentityRealm, such as tenant-pjsabbe or tenant-tvdk.
  • Keycloak:AdminRealm identifies the realm that issues the backend provisioning token. It defaults to master.
  • Keycloak:AdminClientId and Keycloak:AdminClientSecret identify the backend-only organizor-provisioner service account in that admin realm.

The API constructs the platform issuer from Keycloak:BaseUrl and Keycloak:PlatformRealm, then accepts only that issuer and issuers of active catalog tenant realms. It validates the organizor-api audience and never follows OpenID metadata from an issuer supplied by an untrusted token. There is no API setting named Keycloak:Authority or Keycloak:Realm in this model.

Example development shape:

{
  "Keycloak": {
    "BaseUrl": "https://localhost:8443",
    "PlatformRealm": "organizor-dev",
    "AdminRealm": "master",
    "AdminClientId": "organizor-provisioner",
    "AdminClientSecret": "<provisioner-client-secret>",
    "DefaultTenantAdminTemporaryPassword": "<optional-local-only-password>",
    "DevelopmentAdmin": {
      "Username": "admin@organizor.dev",
      "Email": "admin@organizor.dev",
      "Password": "<local-only-organizor-admin-password>"
    }
  }
}

BaseUrl must be the canonical Keycloak HTTP(S) base URL. A mismatch between http and https changes the issuer and makes token validation fail with 401 Unauthorized.

The development API accepts the local self-signed Keycloak certificate for metadata and admin-client calls. This is development-only behavior and must not be used for production identity-provider calls.

Store the provisioner secret in user secrets, environment variables, or deployment secret storage. It must never appear in the portal, a tenant website, or a public auth-discovery response. Use Keycloak Setup to bootstrap the local provisioner after a Keycloak reset.

Outside Development, the API refuses to start when the Keycloak base URL, platform realm, admin client id, or admin client secret is missing, non-HTTPS where required, or uses a loopback URL. Keycloak:AdminRealm is optional and defaults to master; setting it explicitly is useful for clarity or an intentionally different administration realm.

Keycloak:DefaultTenantAdminTemporaryPassword is optional and supported only in Development for predictable local testing. When omitted, onboarding generates a unique temporary password for the default {slug}-admin user. Production refuses to start if this setting is configured.

In Development, the API can seed the configured Keycloak:DevelopmentAdmin:Username with the platform-realm organizor-admin role when Keycloak:DevelopmentAdmin:Username, Keycloak:DevelopmentAdmin:Email, and Keycloak:DevelopmentAdmin:Password are configured. Store development-admin values in user secrets, not Docker .env files or source. Existing users keep their current password unless Keycloak:DevelopmentAdmin:ResetPasswordOnStartup is explicitly set to true.

Portal UI

The current Blazor WebAssembly portal is the central Organizor-admin control plane. It uses the platform realm and calls the API with platform-realm bearer tokens.

The portal reads these values from wwwroot/appsettings.json or the matching environment-specific Blazor configuration file:

  • Api:BaseUrl
  • Portal:PlatformBaseUrl
  • Keycloak:Authority
  • Keycloak:ClientId
  • Authentication:RedirectUri
  • Authentication:PostLogoutRedirectUri

Keycloak:Authority remains a browser-client setting, not an API setting. Its local value is https://localhost:8443/realms/organizor-dev.

Current local development endpoints:

Setting Value
Portal URL https://localhost:7025
Platform Keycloak authority https://localhost:8443/realms/organizor-dev
Portal client ID organizor-ui
Login callback https://localhost:7025/authentication/login-callback
API base URL https://localhost:7184

These values must stay aligned with the organizor-ui client redirect URIs and web origins in the platform realm. Portal:PlatformBaseUrl identifies that one fixed host. At every other Portal host, startup resolves and validates a trusted tenant-specific runtime configuration and tenant-local client through the anonymous portal auth contract; it never falls back to the platform configuration.

Quartz

Quartz uses the Catalog connection string for its persistent store. The same catalog database stores tenant records and Quartz scheduler tables.

The API registration configures:

  • PostgreSQL-backed Quartz persistence;
  • Newtonsoft JSON serialization for persisted job data;
  • clustering support;
  • hosted service startup for Quartz background processing.

Tenant job scheduling is not enabled on application startup yet. TenantJobScheduler is available for future real tenant jobs, but the startup scheduling block is currently commented out until those jobs exist.

Logging

Serilog is configured in appsettings.json.

Current sinks:

  • console;
  • rolling file logs under logs/log-.txt.

Log output includes tenant and request correlation properties when available:

  • Id;
  • Slug;
  • DatabaseName;
  • CorrelationId.

Identity lifecycle logs additionally identify the catalog tenant realm where useful. Never log provisioner secrets or bearer tokens.

CORS

The API selects a CORS policy by environment:

  • DevCors in development allows any origin, header, and method.
  • ProdCors outside development dynamically allows origins from active tenant website configuration in the catalog.

Production CORS uses tenant auth.webOrigins values and the origin of website.baseUrl as the allow-list source. Wildcards, malformed origins, URL fragments, non-origin webOrigins, and non-local HTTP origins are rejected. CORS is not authorization; bearer tokens, issuer-aware role policies, tenant resolution, and issuer-to-tenant checks still enforce API access.

OpenAPI and Scalar

OpenAPI and Scalar endpoints are mapped only in development. This keeps the production surface smaller while retaining local API exploration during development.
