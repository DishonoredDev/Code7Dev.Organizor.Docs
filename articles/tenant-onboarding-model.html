Tenant Onboarding Model

The preferred full tenant creation route is:

POST /api/admin/tenants/onboard

It creates the catalog record, assigns an immutable tenant Keycloak realm, stores centralized website/auth settings and a tenant-admin portal base URL, provisions tenant identity resources, creates the tenant database, applies migrations, installs the selected plan's included modules, and marks the tenant Active only after the workflow succeeds.

Catalog Identity Mapping

Every tenant owns one Keycloak realm. The catalog assigns Tenant.IdentityRealm deterministically as tenant-{normalized-slug} before the tenant is persisted:

Tenant Slug Identity realm
PJsabbe pjsabbe tenant-pjsabbe
TVDK tvdk tenant-tvdk
Acme acme tenant-acme

IdentityRealm is a required, unique, immutable catalog field. AdminPortalBaseUrl is a nullable, unique catalog field: catalog-only creation may leave it empty, but full onboarding requires it. Neither is an editable tenant JSON setting or inferred from a token or HTTP request.

Flow

flowchart TD
    A[Onboard request] --> B[Create catalog tenant as Pending with IdentityRealm]
    B --> C[Store centralized website/auth settings]
    C --> D[Create or reuse tenant Keycloak realm]
    D --> E[Create realm-local roles and /admins,/users groups]
    E --> F[Create API-audience, tenant website, and tenant portal clients]
    F --> G[Create tenant database]
    G --> H[Apply tenant migrations]
    H --> I{Provisioning successful?}
    I -->|Yes| J[Mark tenant Active]
    J --> K[Install included modules]
    K --> L{Every included module enabled?}
    L -->|Yes| M[Create default realm-local tenant admin]
    M --> N[Onboarding succeeds]
    L -->|No| O[Mark tenant Failed: recoverable module failure]
    O --> P[Admin repairs and retries included modules]
    P --> L
    I -->|No| Q[Mark tenant Failed]

The Keycloak provisioning token is obtained by the backend-only organizor-provisioner service account in the master realm. Platform administrators use their normal platform-realm login and do not receive Keycloak master credentials.

Tenant Realm Contents

For tenant acme, onboarding creates or reuses tenant-acme and ensures:

  • realm roles tenant-admin and tenant-user;
  • realm-local /admins and /users groups, mapped to those roles;
  • the internal organizor-api audience client;
  • public PKCE client tenant-acme-web;
  • public PKCE client tenant-acme-portal;
  • default tenant admin acme-admin in /admins.

There is no /tenants/acme/... group hierarchy. The realm itself is the tenant boundary. The same username or email can therefore be used independently in different tenant realms.

Initial Tenant Administrator Credential

The default administrator is created only after tenant database provisioning and included-module installation both succeed. When it is newly created, the successful POST /api/admin/tenants/onboard response includes its username and temporary password once, with Cache-Control: no-store. The portal shows a copyable one-time notice. The credential is never stored in the catalog, tenant settings, logs, or tenant list responses; dismissing the notice removes it from the portal's in-memory page state.

Creating or reusing an existing default administrator never resets its password and does not return a credential. If the response is lost after the Keycloak account was created, the password cannot be recovered. Likewise, a tenant whose module installation initially failed may later recover without an automatically issued default administrator. In either case, create a replacement realm-local tenant-admin through POST /api/admin/tenants/{tenantId}/users with a temporary password and required UPDATE_PASSWORD action. If the tenant user limit is one, remove the stranded default account before adding the replacement. This API recovery path also works while the tenant is Failed; the portal user-management screen selects active tenants only.

Plan Selection And Included Modules

The onboarding request accepts an optional planKey. When no plan key is supplied, Organizor assigns starter. The selected plan must be active.

After provisioning succeeds, Organizor installs every module included by the selected plan in dependency order. Optional plan modules are not installed automatically; an Organizor administrator can add them later from the tenant module control plane. If included-module installation fails, the tenant is marked Failed with a recoverable module failure; only its included modules can be repaired, installed, re-enabled, or retried until the whole included bundle is enabled. Failed provisioning leaves the tenant inactive and its modules unavailable.

The starter plan includes activities; the pro plan includes the full PJsabbe/TVDK family-activity bundle. Plan entitlement and tenant installation are separate from legacy features and settings JSON. See Tenant Modules for the catalog and operator workflow.

Website And Auth Settings

Onboarding accepts tenant website/auth settings for separate tenant UI projects:

Field Purpose
websiteBaseUrl Public tenant website base URL.
loginRedirectUris OIDC login callback URLs allowed by the tenant website client.
logoutRedirectUris Post-logout redirect URLs allowed by the tenant website client.
webOrigins Browser origins allowed by the tenant website client. Defaults to the website origin when omitted.
registrationRedirectUrl Optional tenant website URL used after registration flows.

In the platform onboarding dialog, entering a valid websiteBaseUrl suggests editable values for the four related fields: {base}/authentication/login-callback, {base}, the website origin, and {base}/register/complete. The base path is retained in callback URLs, while the web origin contains only scheme, host, and optional port. A later base URL change updates only fields that still use a portal suggestion, so an operator's manual customization is preserved. Reset suggested values deliberately reapplies all four values from the current base URL.

These values are stored in tenant settings under website and auth. Organizor also stores a generated auth.clientId using tenant-{slug}-web and provisions that public client in the tenant's own realm. The realm identifier itself remains the immutable relational Tenant.IdentityRealm, not JSON configuration.

The tenant public client uses Authorization Code Flow with PKCE. It emits realm roles, aud: organizor-api, and a direct tenant claim containing the tenant slug for client compatibility. The API does not use the tenant claim to decide tenant access; it binds the JWT issuer to the catalog identity realm.

Tenant websites must obtain their authority and client id from GET /api/public/tenants/{slug}/auth.

Tenant Admin Portal URL

Full onboarding also requires tenantAdminPortalBaseUrl, for example https://localhost:7022 for local TVDK administration. It is a normalized, unique HTTPS base URL (with the existing local HTTP allowance), stored relationally as AdminPortalBaseUrl rather than in tenant JSON settings. The platform onboarding form keeps it visibly separate from the public website base URL and does not infer a production admin host from that website.

The URL provisions a separate tenant-{slug}-portal client in the tenant's own realm. Its only redirect URI is {portalBaseUrl}/authentication/login-callback; its post-logout redirect URI is {portalBaseUrl}; and its web origin is the portal URL origin. The client uses Authorization Code Flow with PKCE and the same realm-role, organizor-api audience, and direct tenant-claim mappers as the website client.

At the tenant portal host, the Portal loads GET /api/public/tenant-portals/auth?baseUrl=... before OIDC startup. That contract returns public configuration only and must match the actual host exactly. The central platform host remains fixed to the platform realm and never chooses a tenant realm from a user input.

Catalog-Only Creation

POST /api/v1/tenants creates only the catalog record with Pending status and assigns its deterministic IdentityRealm. It does not create the Keycloak realm, users, groups, clients, or tenant database.

Deletion Lifecycle

Soft deletion first disables the tenant realm. If Keycloak cannot disable it, Organizor keeps the catalog tenant active and returns TENANT_IDENTITY_PROVIDER_FAILED. Once soft-deleted, the tenant is removed from the API issuer allow-list, so previously issued tenant tokens are rejected immediately.

Hard deletion is intentionally guarded: the tenant must already be soft-deleted. The workflow executes in this order:

  1. Delete the complete tenant realm, including users, sessions, roles, groups, and clients.
  2. Drop the tenant database.
  3. Remove the catalog record.

A missing tenant realm is treated as already deleted so a partial cleanup can be retried. If realm deletion fails, database and catalog deletion do not run and the operation returns TENANT_IDENTITY_PROVIDER_FAILED.
