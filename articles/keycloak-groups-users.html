Keycloak Groups And Users

Each tenant has its own Keycloak realm. Tenant identities do not use the old shared /tenants/{slug} group hierarchy.

For tenant acme, onboarding creates realm tenant-acme with:

  • realm roles tenant-admin and tenant-user;
  • group /admins mapped to tenant-admin;
  • group /users mapped to tenant-user;
  • tenant website client tenant-acme-web;
  • an internal organizor-api audience client;
  • after successful database and included-module provisioning, default tenant admin acme-admin in /admins.

The same username or email can be created in tenant-pjsabbe and tenant-tvdk because Keycloak uniqueness is realm-local. Their user IDs, credentials, sessions, and role assignments are independent.

Platform Administrators

Platform administrators live only in the configured platform realm (organizor-dev locally) and carry organizor-admin. They manage tenant realms through the Organizor portal and API; they do not sign into each tenant realm or the Keycloak master realm.

Tenant Claims And Roles

Tenant website clients emit:

  • realm roles so tenant users receive tenant-user or tenant-admin;
  • aud: organizor-api for API token validation;
  • a direct tenant claim containing the tenant slug for client compatibility.

The API does not use the tenant claim as its isolation boundary. It binds each tenant-scoped request to the JWT issuer and the catalog-owned tenant realm.

Lifecycle

  • Soft delete disables the tenant realm and removes it from API token issuer allow-listing.
  • Hard delete removes the complete tenant realm, including all users, sessions, groups, roles, and clients, before deleting the tenant database and catalog record.
  • Removing one tenant user affects only that realm-local identity. It cannot remove or disable a user in another tenant realm.
