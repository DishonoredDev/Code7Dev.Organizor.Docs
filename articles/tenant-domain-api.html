Tenant Domain API

Tenant domain endpoints are tenant-scoped and require:

  • Authorization: Bearer <token>
  • X-Tenant-Slug: <tenant-slug>

Unless stated otherwise, these endpoints require a token satisfying the tenant-admin role policy and tenant access middleware verifies that the user belongs to the tenant selected by the header.

People And Relationships

Relationship direction is from the responsible/contact person to the child or related person:

  • fromPersonId: parent, guardian, emergency contact, or other responsible person.
  • toPersonId: child participant or related person.

Supported relationship types are Parent, Guardian, Mother, Father, StepParent, EmergencyContact, and Other.

Endpoint Purpose
GET /api/v1/people List tenant-local people.
POST /api/v1/people Create a tenant-local person.
PUT /api/v1/people/{personId} Update a tenant-local person.
POST /api/v1/people/{personId}/link-user Link a tenant-local person to an existing tenant user id.
POST /api/v1/people/{personId}/unlink-user Clear the tenant user link for a person.
GET /api/v1/people/{personId}/relationships List relationships connected to a person.
POST /api/v1/people/{personId}/relationships Create a relationship from personId to the request target.
PUT /api/v1/people/{personId}/relationships/{relationshipId} Update relationship type and flags.
POST /api/v1/people/{personId}/relationships/{relationshipId}/activate Mark a relationship active.
POST /api/v1/people/{personId}/relationships/{relationshipId}/deactivate Mark a relationship inactive.
POST /api/v1/people/{personId}/relationships/{relationshipId}/archive Archive a relationship.
GET /api/v1/me/children List active children managed by the current linked parent or guardian person.

Relationship validation returns stable error codes:

Error Meaning
PERSON_NOT_FOUND The route or request person does not exist in the resolved tenant database.
PERSON_LINKED_USER_ID_REQUIRED The link request did not include a non-blank linked user id.
PERSON_LINKED_USER_CONFLICT The linked user id is already assigned to another person in the tenant.
PERSON_RELATIONSHIP_NOT_FOUND The requested relationship does not exist for the route person.
PERSON_RELATIONSHIP_SELF_REFERENCE The source and target person are the same.
PERSON_RELATIONSHIP_ALREADY_EXISTS An active relationship with the same source, target, and type already exists.
PERSON_RELATIONSHIP_PRIMARY_CONTACT_CONFLICT The child already has an active primary-contact relationship.
PERSON_RELATIONSHIP_INVALID The relationship request is invalid.

Organizations

Tenant organizations are tenant-local records used by activity setup and document capability eligibility.

Endpoint Purpose
GET /api/v1/organizations List tenant-local organizations.
POST /api/v1/organizations Create a tenant-local organization.
PUT /api/v1/organizations/{id} Update a tenant-local organization.

Organization records include name, type, status, contact fields, optional KBO number and bank account, and structured address data.

Activities can reference an activity type and optionally a tenant-local organization.

Tenant admins can configure public activity page content separately from operational activity setup:

Endpoint Purpose
GET /api/v1/activities/{id}/public-detail Load tenant-admin public detail content JSON for one activity.
PUT /api/v1/activities/{id}/public-detail Replace tenant-admin public detail content JSON for one activity.
GET /api/v1/activity-public-page-templates List backend-provided public page templates.
POST /api/v1/activities/{id}/public-detail/apply-template Replace one activity's public detail content with an editable copy of a template.
GET /api/v1/public/activities/{activityId} Anonymous public-safe activity detail response for separate public websites.

The public detail response contains a fixed hero object for the activity page, followed by ordered content blocks. The hero uses activity defaults unless tenant admins enable a hero override in the portal. Supported first-slice block types include richText, practicalInfo, schedule, tabs, faq, testimonial, gallery, and registrationCta; new authoring should prefer practical information tabs over standalone tabs, with those tabs presented above the general information rows. Gallery blocks may include a displayMode of grid or slideshow. Registration CTA blocks should render a visible registration action. Public websites should render hero before ordered blocks and ignore unknown future block types.

Public page templates are backend-owned presets that use the same public detail block JSON contract. The current catalog exposes one standard activity page template for the TVDK-style public website layout. Applying a template copies the template content into the activity; the activity then owns its editable content independently from later template changes.

Template listing is tenant-admin authorized but does not require tenant database resolution because templates are static backend presets. Applying a template remains tenant-scoped and requires the selected tenant context.

Registration Validation Rules

Validation rules are configured per activity type or per activity. Activity-level rules replace activity-type rules when they use the same rule key. The current slice stores these rules in the existing tenant JSON configuration fields instead of a separate table.

Supported rule types:

  • required
  • required-when
  • age-range
  • regex
  • numeric-range
  • accepted-boolean

required-when condition values are fixed to:

  • present
  • missing

Supported targets are limited to core registration fields in this slice:

  • participant data such as participant.firstName, participant.lastName, participant.email, participant.phoneNumber, participant.dateOfBirth, participant.address, and participant.nationalNumber
  • contact data such as contact.firstName, contact.lastName, contact.email, contact.phoneNumber, contact.dateOfBirth, contact.address, and contact.nationalNumber
  • registration.linkedUserId
Endpoint Purpose
GET /api/v1/activity-types/{activityTypeId}/registration-validation-rules Load activity-type validation rules.
PUT /api/v1/activity-types/{activityTypeId}/registration-validation-rules Replace activity-type validation rules.
GET /api/v1/activities/{activityId}/registration-validation-rules Load activity validation rules.
PUT /api/v1/activities/{activityId}/registration-validation-rules Replace activity validation rules.

Public registration submissions reject invalid payloads with REGISTRATION_VALIDATION_FAILED and a structured violations extension payload. Invalid rule configuration is rejected with REGISTRATION_RULE_INVALID, REGISTRATION_RULE_CONFLICT, or REGISTRATION_RULE_FIELD_UNKNOWN before the rules are saved.

Registration Confirmation Email

Tenant admins can configure confirmation email templates for activity types and activity-specific overrides. Activity templates override activity-type templates for the same culture. If no enabled template exists, public registration succeeds and returns confirmationStatus as not_configured.

Confirmation templates are stored in the shared tenant email_templates table with purpose RegistrationConfirmation; delivery attempts are stored in email_deliveries with the same purpose.

For child or dependent registrations, the default recipient is the active primary parent or guardian. Until every public registration creates structured parent/guardian relationships, confirmation rendering can fall back to submitted parent data in Registration.CoreDataJson:

  • parentFirstName
  • parentLastName
  • parentEmail
  • parentPhone

Templates support double-brace variables such as {{participant.fullName}}, {{contact.fullName}}, {{activity.name}}, {{registration.paymentStatus}}, and {{tenant.slug}}. Unknown variables are rejected when saving, previewing, or sending. HTML templates reject unsafe script, event handler, JavaScript URL, form, and iframe content.

Endpoint Purpose
GET /api/v1/activity-types/{activityTypeId}/confirmation-templates List activity-type confirmation templates.
PUT /api/v1/activity-types/{activityTypeId}/confirmation-templates/{culture} Create or update an activity-type template.
GET /api/v1/activities/{activityId}/confirmation-templates List activity override templates.
PUT /api/v1/activities/{activityId}/confirmation-templates/{culture} Create or update an activity override template.
DELETE /api/v1/activities/{activityId}/confirmation-templates/{culture} Delete an activity override template.
POST /api/v1/registrations/{registrationId}/confirmation-email/preview Render a confirmation email without sending it.
POST /api/v1/registrations/{registrationId}/confirmation-email/send-test Send a test email and log the attempt.
POST /api/v1/registrations/{registrationId}/confirmation-email/resend Send the confirmation email again and log the attempt.
GET /api/v1/registrations/{registrationId}/confirmation-email/deliveries List confirmation delivery attempts for a registration.

POST /api/v1/activities/{activityId}/public-registrations attempts confirmation delivery after the registration is persisted. Delivery failure does not roll back registration creation. The public response includes confirmationStatus with one of:

  • not_configured
  • sent
  • failed

Confirmation email uses the same tenant SMTP settings as document delivery under settings.email.smtp. SMTP credentials are never returned by confirmation endpoints. Preview intentionally returns rendered content and is restricted to tenant admins.

Endpoint Purpose
GET /api/v1/activities/{activityId}/registrations List registrations for an activity.
GET /api/v1/registrations/{id} Load one registration.
POST /api/v1/registrations/{id}/confirm Confirm a submitted registration.
POST /api/v1/registrations/{id}/cancel Cancel a registration.

GET /api/v1/me/activities List active activities available to the current tenant user.
GET /api/v1/me/activity-types List active activity types and fields available to the current tenant user.

Cancelled registrations reject later confirmation and payment updates.

Parent-managed registrations require the current linked user to resolve to a parent or guardian person and to have an active relationship to the selected child with CanManageRegistrations set to true. The participant stays the child person; the linked user stays the parent or guardian account.

Registrations reject a second non-cancelled registration for the same person and activity with REGISTRATION_ALREADY_EXISTS. A cancelled registration does not block a later registration.

Activities with positive capacity reject new public and parent-managed registrations once the non-cancelled registration count reaches capacity. Capacity 0 is treated as unlimited. Full activities return ACTIVITY_CAPACITY_FULL.

These parent-managed endpoints require the tenant-user role. Tenant admin rights alone do not grant child registration access.

Document Capabilities

The first supported capability keys are:

  • fiscal-attestation
  • healthcare-attestation

Capabilities are assigned per activity type. Assignments are stored as tenant-local normalized data with optional optionsJson for capability-specific template or display configuration.

Endpoint Purpose
GET /api/v1/activity-types/{activityTypeId}/document-capabilities List document capabilities configured for an activity type.
PUT /api/v1/activity-types/{activityTypeId}/document-capabilities Replace document capability assignments for an activity type.
GET /api/v1/registrations/{registrationId}/document-eligibility Evaluate enabled document capabilities for a registration.
GET /api/v1/registrations/{registrationId}/documents/{capabilityKey}/download Generate and download a PDF for an enabled document capability.
POST /api/v1/registrations/{registrationId}/documents/{capabilityKey}/send Generate and email a PDF for an enabled document capability.

Eligibility is evaluated on demand. It returns one result per enabled capability with:

  • isEligible
  • stable missingDataCodes
  • stable blockingReasonCodes

Fiscal and healthcare eligibility require the activity to have ended, the registration to be non-cancelled, complete child person data, a primary active parent/guardian relationship when parent data is required, and the connected organization data required by the selected capability.

Document download and delivery currently support fiscal-attestation and healthcare-attestation. Generation is tenant-local, returns application/pdf, and does not persist generated documents. The backend fills PJSabbe-compatible PDF templates from the runtime documents folder: template_fiscalefiche_{activityStartYear}.pdf for fiscal attestations and template_healthcare_2024.pdf for healthcare attestations. Structured parent or guardian data from active primary person relationships takes precedence. Until all registrations have structured relationship data, generation can also read temporary parent data from Registration.CoreDataJson with:

  • parentFirstName
  • parentLastName
  • parentDateOfBirth
  • parentNationalNumber
  • parentEmail
  • parentAddress

Document delivery uses effective tenant configuration under settings.email.smtp:

{
  "email": {
    "smtp": {
      "host": "smtp.gmail.com",
      "port": 465,
      "useSsl": true,
      "senderEmail": "noreply@example.org",
      "senderName": "Example Club",
      "username": "noreply@example.org",
      "password": "<tenant-smtp-secret>"
    }
  }
}

Use tenant overrides or deployment secrets for SMTP credentials. Do not commit real provider secrets to appsettings files.

Address objects must include street, number, zipCode or postalCode, city, and countryCode or country.
