Tenant Modules

Organizor is a modular monolith: one deployed API and one database-per-tenant platform, with a code-owned module catalog. It does not load third-party assemblies at runtime or split every module into a microservice.

A module answers a product-composition question: which business workflows a tenant can use. It is deliberately separate from tenant settings, user roles, and sport labels.

Five Separate Concerns

Question Owner Source of truth
Is code available in this deployment? Module registry Compiled, startup-registered module definition.
Is the module part of a plan or available as an add-on? Tenant plan Plan-module entitlement.
Has a tenant activated the module? Tenant installation Tenant-module installation record.
May a user perform an action? Authorization and tenant access Existing roles and tenant-access checks.
How should an active module behave? Module-owned configuration Typed, validated configuration contract.

A module is available to tenant-owned behavior only when its code is deployed, the tenant plan entitles it, the tenant has an installation record in Enabled state, and all of its dependencies are enabled. API enforcement is server-side; hiding a portal navigation item is not security.

The first foundation slice exposes the reusable availability gate, but does not retroactively gate every existing compatibility endpoint. Existing module-owned endpoints are attached to the gate in their own rollout work so existing tenants are not silently broken before their installation state is explicitly configured.

Module Catalog

The initial catalog is organized by business workflow, not by sport or customer brand.

Key Purpose Required modules
activities Activity types, activities, schedules, pricing, capacity, and public activity content. None
registrations Registration forms, validation, capacity, status, payment tracking, and confirmations. activities
participants-families People, guardian/parent-child relationships, contact responsibility, and reusable family data. None
parent-self-service Guardian access to managed children, child registration, registration visibility, and permitted cancellation. registrations, participants-families
organizations Tenant organization records, including legal issuer data used by qualifying workflows. None
attestations Activity-type attestation eligibility and fiscal or healthcare document workflows. activities, registrations, participants-families, organizations

Football, swimming, camps, training, and EAD lessons are tenant-local activity types and activity configuration. They are not modules.

PJsabbe and TVDK therefore use the same full bundle:

activities
registrations
participants-families
parent-self-service
organizations
attestations

They differ through their activity types, organization/legal-issuer data, public content, and other typed tenant settings. A future tenant can select a smaller compatible bundle, such as activities alone or activities and registrations.

Plans And Tenant Installations

A plan has one entitlement for every deployed module:

Entitlement Meaning
Included The plan supplies the module. It is installed automatically during successful onboarding.
Optional A platform administrator can install it later as a tenant add-on.
Unavailable The plan cannot activate the module.

The seeded plans are intentionally simple:

Plan Included modules Add-ons
starter activities All other initial modules are optional.
pro The full PJsabbe/TVDK family-activity bundle. None in the initial catalog.

Each tenant installation records its source (PlanIncluded or PlanAddOn) and its state:

State Meaning
Installing Installation has started. If an interruption leaves it in this state, an operator can retry it.
Enabled The module can be used, subject to normal authorization.
Disabled The module is intentionally inactive; its business data is retained.
Failed Installation failed and records a machine-readable reason; an operator can retry it.

Installing a module requires an active tenant, a plan entitlement, and enabled dependencies. A tenant whose provisioning completed but whose included modules failed can recover only its included modules until the full included bundle is enabled. An enabled module cannot be disabled while another enabled module depends on it. Re-enabling preserves module business data. Changing a plan entitlement to Unavailable is blocked while an enabled, failed, or installing non-exception tenant installation still uses that entitlement; disable the module first or choose a compatible plan.

Onboarding

POST /api/admin/tenants/onboard accepts an optional planKey. When omitted, Organizor uses starter. The requested plan must exist and be active.

{
  "name": "TVDK",
  "slug": "tvdk",
  "planKey": "pro",
  "authSettings": {
    "websiteBaseUrl": "https://www.example.org"
  }
}

After Keycloak provisioning, tenant database creation, and tenant migrations succeed, Organizor installs every included module in dependency order. Optional modules remain a deliberate platform-admin action. If included-module installation fails, the tenant is marked Failed with a recoverable module-installation reason; the platform admin can repair and retry its included modules, and the tenant becomes active once they are all enabled. A failed tenant onboarding does not make its modules available.

Existing tenants are not inferred from legacy feature flags or JSON settings. A platform administrator configures their installations explicitly during the transition.

Platform Operator API

All module-management routes are catalog-scoped, require organizor-admin, and do not use X-Tenant-Slug.

Inspect the deployed catalog

GET /api/admin/modules
Authorization: Bearer <organizor-admin-token>

Returns every code-deployed module with its stable key, display metadata, version, and dependencies.

Manage plan bundles

GET /api/admin/tenant-plans/{planKey}/module-entitlements
PUT /api/admin/tenant-plans/{planKey}/module-entitlements
Authorization: Bearer <organizor-admin-token>

The PUT body replaces the plan's complete entitlement set atomically. It must include every deployed module and use Included, Optional, or Unavailable for each one.

{
  "modules": [
    { "moduleKey": "activities", "availability": "Included" },
    { "moduleKey": "registrations", "availability": "Optional" },
    { "moduleKey": "participants-families", "availability": "Optional" },
    { "moduleKey": "parent-self-service", "availability": "Optional" },
    { "moduleKey": "organizations", "availability": "Optional" },
    { "moduleKey": "attestations", "availability": "Optional" }
  ]
}

Manage a tenant's installed modules

GET  /api/admin/tenants/{tenantId}/modules
POST /api/admin/tenants/{tenantId}/modules/{moduleKey}/install
POST /api/admin/tenants/{tenantId}/modules/{moduleKey}/retry
POST /api/admin/tenants/{tenantId}/modules/{moduleKey}/enable
POST /api/admin/tenants/{tenantId}/modules/{moduleKey}/disable
Authorization: Bearer <organizor-admin-token>

The list response provides each module's plan availability, installation state/source/failure reason, dependency state, and the actions currently permitted to the operator. Install, retry, enable, and disable return the updated module record.

Relevant stable errors include TENANT_MODULE_NOT_FOUND, TENANT_MODULE_NOT_ENTITLED, TENANT_MODULE_DEPENDENCY_NOT_ENABLED, TENANT_MODULE_INVALID_STATE, TENANT_MODULE_PLAN_CONFLICT, and TENANT_MODULE_TENANT_NOT_ACTIVE.

Platform Portal Workflow

The platform portal presents module lifecycle in plain language:

  • The Plans page has a Modules tab where an Organizor admin selects Included, Optional add-on, or Unavailable for every deployed module.
  • The tenant onboarding dialog lists active plans and sends the chosen planKey.
  • The tenant detail drawer has a Modules section showing entitlement, installation state, source, dependencies, and a contextual Install, Retry, Enable, or Disable action.

Tenant administrators continue to manage only the typed settings that an enabled module explicitly delegates to them. They do not manage plan entitlements or tenant module lifecycle.

Configuration And Legacy JSON

The existing tenant_plans.features, tenant_plans.settings, tenants.features, and tenants.settings JSONB-backed configuration remains supported as a compatibility layer. It still supplies effective legacy config through the existing system defaults -> plan defaults -> tenant overrides merge.

That JSON is not the module system:

  • Do not use a generic feature flag to decide whether a tenant has a module.
  • Do not store module installation state, entitlement, authorization, queryable limits, or secrets in an arbitrary JSON editor.
  • Use a typed, validated module contract for settings owned by a module. Bounded, validated JSONB can still be appropriate for optional module settings, but it never determines module availability.
  • SMTP and OIDC are integrations with typed configuration and write-only/redacted secrets; they are not sellable modules.

The first migration preserves existing JSON values and does not reinterpret them as installations. A later migration will classify each existing feature flag as a temporary release flag, module entitlement, module setting, or obsolete configuration before retirement.

Catalog Persistence

Module lifecycle metadata lives in the catalog database; module business data remains in the tenant database.

Table Key columns Purpose
tenant_plan_module_entitlements plan_key, module_key, availability, timestamps One entitlement per deployed module for each plan. plan_key references tenant_plans.key.
tenant_module_installations tenant_id, module_key, state, source, failure_reason, timestamps One lifecycle record per installed tenant module. tenant_id references tenants.id.

Both tables use composite primary keys of their two identity columns. Deleting a plan or tenant cascades its matching catalog module metadata. The installation table is indexed by tenant and state for operator and availability lookups.

Startup seeding creates missing initial plans and missing entitlement rows, but does not overwrite operator-managed plan metadata, settings, or entitlement choices.

Relationship To Activity Attestations

The attestations module enables the capability family, but it does not make every activity eligible. Tenant administrators configure fiscal and healthcare capabilities per activity type. For the PJsabbe and TVDK composition, eligible camps can enable attestations while football, swimming, and EAD training types remain ineligible unless their own accepted rules say otherwise.

Historical registration and attestation input must be preserved when people or guardian relationships later change. The separate PJsabbe import and historical snapshot migration is deferred to its own feature.
