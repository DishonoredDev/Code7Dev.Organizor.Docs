API Authentication

Overview

The API accepts Keycloak JWTs from a controlled set of realms, not from arbitrary OpenID Connect issuers:

  • the configured platform realm (organizor-dev locally);
  • the realm mapped to an active catalog tenant, such as tenant-pjsabbe or tenant-tvdk.

The API checks the catalog mapping before fetching OpenID metadata or signing keys. A token cannot make the API contact an arbitrary issuer URL.

JWT Validation

Every accepted token must be:

  • signed by the allow-listed realm's keys;
  • issued by that exact realm;
  • unexpired;
  • addressed to the organizor-api audience.

OpenID metadata and signing keys are cached per trusted issuer. The active tenant realm mapping is checked on authentication so a soft-deleted tenant's already-issued token is rejected immediately by the API.

Roles And Issuers

  • organizor-admin is a platform role. It grants platform administration only when issued by the platform realm.
  • tenant-admin and tenant-user are tenant-realm roles.
  • A tenant realm cannot gain platform access merely by defining a role named organizor-admin.

The platform portal uses a single platform-realm login. The backend master-realm service account is never used as a browser login.

Service Accounts

The master-realm organizor-provisioner client is used only by the backend to call Keycloak Admin REST endpoints. Its secret must never be sent to a browser.

An internal organizor-api service account does not bypass issuer binding by itself. It must satisfy the same issuer-aware route policy as any other caller; cross-tenant support remains restricted to a platform-realm organizor-admin identity.

Error Codes

  • 401 Unauthorized: missing, expired, invalidly signed, unknown-issuer, or wrong-audience token.
  • 403 Forbidden: valid token from the wrong tenant realm or without the required role.
  • 400 Bad Request: missing or invalid tenant header on a tenant-scoped route.
