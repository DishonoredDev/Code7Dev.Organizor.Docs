Role-Based Authorization

Overview

The API authorizes requests with issuer-aware ASP.NET Core policies backed by Keycloak realm roles. Authentication validates the JWT first, tenant access middleware binds a tenant-scoped request to its catalog-owned realm, and endpoint authorization policies apply the issuer-appropriate role rule.

A role string alone never grants access. The realm that issued it matters.

Realm Roles

Role Owning realm Purpose
organizor-admin Platform realm only Platform administrator. Manages catalog tenants and control-plane operations.
tenant-admin Tenant realm only Tenant administrator. Uses tenant-aware application endpoints for that realm.
tenant-user Tenant realm only Tenant member. Uses shared tenant-aware application endpoints for that realm.

Tenant realms contain no platform administrator identities. A tenant realm role named organizor-admin cannot grant control-plane access.

JWT Trust And Role Sources

The API accepts a JWT only when all of the following are true:

  • its issuer is the configured platform realm or an active catalog tenant realm;
  • its signature, expiry, and issuer are valid;
  • it contains aud: organizor-api.

OpenID metadata and signing keys are fetched only after the issuer passes the allow-list. The API maps roles from Keycloak realm_access.roles to ASP.NET Core ClaimTypes.Role:

{
  "iss": "https://localhost:8443/realms/tenant-acme",
  "aud": ["organizor-api"],
  "realm_access": {
    "roles": ["tenant-user"]
  }
}

Client roles from arbitrary Keycloak clients are not the authorization source for Organizor policies. Tenant website clients are configured to emit the required realm roles and API audience.

Policies

Policy Accepted issuer and role
RequireOrganizorAdminRole Platform issuer with organizor-admin only.
RequireTenantUserRole Matching tenant issuer with tenant-admin or tenant-user; a platform organizor-admin is the centralized-support exception.
RequireTenantAdminRole Matching tenant issuer with tenant-admin; a platform organizor-admin is the centralized-support exception.

Use policies for new endpoints unless the endpoint is intentionally authentication-only.

[Authorize(Policy = AuthorizationPolicies.RequireOrganizorAdminRole)]

Tenant Interaction

Role checks do not replace tenant checks. For tenant-scoped routes, a user must pass both:

  • issuer-to-tenant authorization in TenantAccessMiddleware;
  • endpoint role or policy authorization in ASP.NET Core.

This means a tenant-acme token is denied when it sends X-Tenant-Slug: contoso, even when its role is otherwise valid. The tenant claim is a compatibility hint, not evidence of membership. The old behavior that treated a token with no tenant claim as a platform superadmin is removed.

Managing Roles

Platform administrators use the Organizor portal/API with their normal platform login. Tenant users and roles are managed through the selected tenant's Organizor administration endpoints, which target that tenant's catalog-owned realm. The backend organizor-provisioner service account performs Keycloak Admin REST work; its secret and the Keycloak master realm are never browser or tenant administrator credentials.

For local diagnosis, inspect the correct realm in Keycloak:

  • organizor-dev contains platform organizor-admin identities;
  • tenant-{slug} contains that tenant's tenant-admin and tenant-user identities.

Do not use a Keycloak console role assignment as the normal production workflow, because it bypasses Organizor's application-level user management and audit path.
