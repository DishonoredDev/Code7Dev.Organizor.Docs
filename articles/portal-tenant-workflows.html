Portal Tenant Workflows

Tenant business APIs require a token from the resolved tenant's own Keycloak realm, the realm-local tenant-admin role, and X-Tenant-Slug where the route is tenant-scoped. The API validates issuer-to-tenant binding; a tenant claim or group path is not that boundary.

The central Portal host is configured only for the platform realm. The same Portal application serves TenantLayout through a tenant's configured portal host, which resolves a tenant-specific runtime OIDC contract before sign-in. Unless a section explicitly says Platform Administration, the workflows below describe that supported tenant-local portal surface and its tenant API contracts.

Tenant boundary: a tenant portal sends its resolved X-Tenant-Slug for tenant-scoped API calls, but the API authorizes it by the token issuer mapped to the catalog tenant. The old shared-realm automatic-header model must not be used.

The tenant shell groups navigation into Overview, Operations, Directory, and Settings sections. Operations contains activity setup and registration review. Directory contains families and people, organizations, and users. Settings contains tenant configuration and the tenant-admin profile.

Shared List And Detail Pattern

Tenant-admin list pages are list-first: the directory or grid remains readable while selecting a record opens a right-side off-canvas drawer. Selected-record editing and related workflows stay inside that drawer rather than stacking another modal over it. A focused page-level create modal remains appropriate when no record has been selected.

When a list row has several secondary actions, the portal groups them in a text-labelled three-dot overflow menu. Activity setup demonstrates both parts of this pattern. People demonstrates the drawer workflow; its current directory has no secondary row actions that need an overflow menu.

When a list page has four summary metrics, it uses the shared horizontal icon KPI bar. The bar collapses responsively instead of presenting four separate metric cards.

Platform Administration

Platform administrators use /admin as the operational overview for tenant lifecycle, plan availability, catalog health, and recent tenant records. Its four summary metrics use the same horizontal icon KPI bar as the tenant-admin surfaces.

/admin/tenants is list-first: the catalog stays full-width for scanning and filtering, onboarding opens in a focused page-level modal, and selecting a tenant opens a right-side detail drawer. The drawer retains the existing effective configuration view, tenant overrides, upgrade, tenant-user navigation, and lifecycle actions. Secondary row actions are grouped in the existing three-dot action menu; soft and hard deletion keep explicit confirmations.

/admin/plans keeps plan defaults in the existing tabbed editor and makes the configuration order explicit: system defaults, plan defaults, then optional tenant overrides. /admin/users?tenantId={id} remains scoped to one active tenant and uses the same KPI, create-modal, and selected-user drawer pattern; it is not a global user directory.

Dashboard

The /tenant dashboard is a read-only operational overview for tenant admins. It summarizes activity state, upcoming activities, tracked registrations, payment follow-up, capacity usage, people, and active organizations.

The dashboard uses a compact KPI bar, action bar, and tab-style sections for overview, launch readiness, and activity operations. The overview keeps needs-attention as the primary panel, with upcoming activities and recent registrations beside it. The dashboard also shows tenant context, local verification status, last refreshed time, and remembers the last selected tab in browser storage. During first load it shows skeleton placeholders, and when the Organizor API is unreachable it shows one connection state instead of misleading zero metrics. If the tenant public website URL is discoverable from the public auth contract, the action bar includes a public-site link. The launch readiness checklist groups checks into tenant setup, activity setup, registration setup, communication, and parent access. It checks whether the tenant has basic configuration, SMTP settings, activity types, active upcoming activities, registration setup, public activity page content, validation rules, confirmation templates, and parent-managed registration prerequisites. Repeated dashboard rows use small reusable components for consistency. The checklist links each item to the existing management page and is operational guidance only; it is not a persisted launch approval.

The first dashboard slice reuses existing tenant-scoped portal services. Registration metrics are loaded through bounded per-activity calls for current and upcoming activities, so very large tenants may see a scoped summary until a dedicated aggregation API is accepted.

If one dashboard source is unavailable, the page renders available sections and shows a partial-data warning.

Tenant User Management

Tenant administrators can open /tenant/users to manage users for their own tenant. The shared horizontal icon KPI row summarizes total, enabled, tenant-admin, and required-action counts. The page is list-first: it supports client-side search across loaded users, visibly distinguishes roles, sign-in state, and required identity-provider actions, and opens a selected user in a right-side drawer. Create user opens in a focused modal with identity, sign-in setup, and tenant-access sections.

The selected-user drawer keeps enable/disable, role-change, and removal actions close to the record they affect. Removal disables the user's realm-local identity and removes its realm-local role memberships; it cannot delete or disable any identity in another tenant realm. Platform administrators use the same interaction pattern from /admin/users?tenantId={id}, where the selected active tenant remains visible as the scope.

Regular tenant-user accounts do not see either management route.

People

Tenant administrators can open /tenant/people to create and edit tenant-local people and manage directional relationships between them. Relationship direction is from the responsible/contact person to the child or related person.

The page is directory-first. The default Directory tab is the complete canonical list of people. A separate Family tab shows current active family links while keeping each person on one row: responsible adults and contacts, people they manage, relationship type, primary-contact, communication, and registration-management signals remain together. This avoids duplicating a participant under several adults or implying ownership. People with no active family link remain visible in both views. Selecting a row or a linked-person name opens the existing off-canvas right-side detail drawer.

The Family tab loads its people and active relationship links from the tenant-admin GET /api/v1/people/family-directory snapshot. It replaces the previous one-relationship-request-per-person summary preload. Inactive and archived relationship history remains in the selected person's drawer management workflow rather than being presented as a current family connection.

The drawer has overview, relationship, management, and detail tabs for portal login state, responsible adults, managed children, and relationship flags for primary contact, registration management, and communication receipt. Page-level person creation uses a focused modal. Selected-person edit, portal login connect/disconnect, and relationship editing stay inside the drawer as workflow modes so admins do not stack competing overlays.

The people page also lets tenant administrators connect or disconnect the selected person from an existing tenant user login. Parent-managed registration resolves the signed-in parent or guardian through this user-person link.

The page exposes relationship flags for primary contact, registration management, and communication receipt. Only one active primary-contact relationship can exist for a child. Duplicate active relationships with the same source person, target person, and relationship type are rejected.

Parent-Managed Registration

Parent-managed registration is not a portal workflow. Regular tenant users use tenant-specific public UIs such as TVDK for profile, family dashboard, managed-child registration, and child registration cancellation.

Those clients use tenant-user read-only activity endpoints under /api/v1/me instead of tenant-admin activity setup endpoints. The child-registration request submits the child person id plus the activity-specific field payload to the backend. The backend enforces the same validation rules used by public registration and rejects unmanaged child selection.

Organizations

Tenant administrators can open /tenant/organizations to list, create, and edit tenant-local organizations. The shared horizontal icon KPI row summarizes total, active, inactive, and archived records. The directory remains full-width while text, type, and status filters help distinguish those records; archived records remain visible by default. Selecting an organization opens a right-side overview/edit drawer, while page-level creation opens a focused modal.

The portal exposes name, type, status, contact fields, optional KBO number and bank account, and structured address fields. The edit workflow groups identity, contact, address, and administrative details. New organization forms default country to Belgium and create organizations as active. Status changes use the existing update workflow and stay with the selected organization.

Activity Setup

Tenant administrators can open /tenant/activities to manage tenant-local activity setup. The page has Activity Types and Activities tabs.

The activity type tab supports list, create, edit, activate, and deactivate actions. Create and edit open in a right-side off-canvas editor so the configured activity type list stays full-width. Tenant admins can configure registration field definitions, enable fiscal or healthcare document capabilities on existing activity types, and configure default registration confirmation email templates.

The activities tab supports list, create, edit, activate, and deactivate actions. Create and edit open in a right-side off-canvas editor so the configured activity list stays full-width. Activities can reference an activity type and optionally a tenant-local organization. Existing activities can define a registration confirmation email override or delete that override to fall back to the activity type default.

Secondary activity type and activity row actions are grouped in a three-dot menu; selecting the row opens the drawer, so the list does not duplicate Edit as a visible row action.

The public activity page editor can start from the backend-provided standard activity page template. Applying the template replaces the activity public detail content with an editable copy; tenant admins can then adjust the hero, reorder blocks, or add/remove sections for that activity. The editor also exposes explicit quick-add controls for the TVDK-rendered sections: practical information, day schedule, FAQ, testimonial, and gallery.

Registration confirmation templates open in a dedicated reusable mail-template editor page from the activity type and activity rows. The activity setup drawers do not duplicate those template fields. The editor uses a WYSIWYG HTML body field, plain-text body, subject, recipient mode, culture, enable flag, sender name override, and reply-to email.

Registration validation rules now open in a dedicated reusable editor page from the activity type and activity rows. The page is scope-based and concise: it edits backend-enforced rules for the current activity type or activity, shows the effective rule set, and keeps the rule catalog limited to the supported core targets. For regex rules, the editor offers preset helpers for common formats such as digits-only and email-like values, while still allowing a custom pattern when needed.

Registration Management

Tenant administrators can open /tenant/registrations to review registrations for a selected activity. The default queue leads with submitted registrations needing a status decision. Separate queue filters expose payment follow-up (non-cancelled unpaid or pending registrations), confirmed registrations, cancelled registrations, or the complete activity list. Status, payment state, participant, payment reference, and registration id filters remain activity-scoped so the selected activity context stays visible.

The page is list-first. Selecting a registration opens an off-canvas right-side drawer with overview, submitted core data, custom field values, status and manual-payment actions, payment metadata, available audit timestamps, and document actions. Tenant admins can confirm or cancel registrations. They can also mark non-cancelled registrations as paid with an optional payment reference, or mark them unpaid. Cancelled registrations reject later confirmation and payment updates.

Low-frequency document actions are also available through a text-labelled three-dot overflow menu in the list. Fiscal and healthcare attestation downloads return PDF files. Send actions use tenant SMTP settings to email the generated PDF to the parent or guardian email when the selected registration, activity type capability, activity, person, relationship, and organization data are eligible.

Public participant registration submission is API-only in this slice through POST /api/v1/activities/{activityId}/public-registrations.

Registration confirmation preview, test-send, resend, and delivery history are exposed through backend tenant-admin APIs. Dedicated portal controls for those registration-level actions are deferred.

Tenant Config

Tenant admins can open /tenant/config. The page calls GET /api/v1/tenant/config through TenantConfigService.

The default view is operational: it summarizes the resolved plan, enabled feature flags, registration behavior, public website/auth readiness, and SMTP readiness. Tenant mail setup and test delivery remain editable through the existing tenant settings endpoints. Raw effective settings JSON is available from the Diagnostics tab for troubleshooting.

Regular tenant-user accounts should not see tenant configuration in the portal.

Tenant Profile

Tenant admins can open /tenant/profile. A persistent signed-in account summary keeps display name, email, resolved tenant, and access context visible. Profile, Security, and Diagnostics tabs separate routine name updates, Keycloak-backed account actions, and troubleshooting claims.

The Profile tab uses PUT /api/v1/tenant/account-actions/profile to update only Keycloak firstName and lastName; all other identity fields remain read-only. The Security tab explains that Keycloak owns credentials, makes password change available through POST /api/v1/tenant/account-actions/change-password, and keeps unavailable future security controls visibly disabled.

The portal does not collect new passwords and does not expose a direct Keycloak account-console link. Tenant website return navigation remains in the shell account panel. Regular tenant users use tenant-specific public UIs for their own profile and account-action UX. These self-service actions operate only on the caller's own realm-local identity; platform support uses /api/admin/tenants/{tenantId}/users for another user's management.
