Tenancy

Organizor uses catalog-driven, database-per-tenant business data and realm-per-tenant identity data.

The catalog database stores tenant records, plan assignment, config overrides, lifecycle status, soft-delete metadata, database name, and immutable IdentityRealm. Each active tenant has a dedicated PostgreSQL database named from its slug and a dedicated Keycloak realm named tenant-{normalized-slug}.

One Keycloak deployment and database can host all of these realms. A separate Keycloak database per tenant is not required; the realm is the identity isolation boundary.

PJsabbe and TVDK therefore have independent user identities. A person using both has two separate accounts and credentials; a username can be reused because Keycloak uniqueness is realm-local.

Rules Of Thumb

  • Catalog operations use the catalog database.
  • Tenant-scoped operations require X-Tenant-Slug unless the endpoint documents another tenant selection mechanism.
  • Tenant-owned domain data lives in the resolved tenant database.
  • The catalog is the source of truth for the tenant slug, database, and immutable Keycloak IdentityRealm mapping.
  • Tenant realm roles and groups are local: /admins and /users, not a shared /tenants/{slug} hierarchy.
  • API authentication accepts only the platform issuer or active catalog tenant issuers, then binds a tenant-scoped request to the resolved tenant realm.
  • Tenant onboarding is the only workflow that creates catalog state, Keycloak realm access, and tenant database state together.
  • The central portal host is a platform-realm control plane. A tenant-admin Portal host resolves its catalog-owned portal URL, tenant realm, and separate portal client before login.

For a tenant-scoped authenticated request, the API accepts the tenant token only when its issuer is the realm held in the resolved tenant context. A platform organizor-admin is the explicit central-support exception where the endpoint policy permits it.

Superseded shared-realm model: older historical material that refers to /tenants/{slug} Keycloak groups describes the prior implementation. New tenant onboarding uses a separate tenant realm and realm-local groups.
