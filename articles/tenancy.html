Tenancy

Organizor uses catalog-driven, database-per-tenant tenancy.

Tenant Catalog

The catalog database stores tenant metadata through CatalogDbContext. Each tenant includes:

  • Id;
  • Name;
  • Slug;
  • DatabaseName;
  • PlanKey;
  • tenant feature overrides;
  • tenant settings overrides;
  • CreatedAt;
  • Status;
  • FailureReason;
  • soft-delete metadata.

The database name convention is organizor_tenant_{slug}. Slugs are normalized to lowercase before they are stored or used for lookups.

Normal catalog reads exclude soft-deleted tenants. Repository methods can include soft-deleted records when an internal operation explicitly asks for them.

Tenant Plans And Config Overrides

Tenant plans are persisted in the catalog database through the tenant_plans table. A plan defines default feature flags and structured settings for tenants assigned to that plan.

Each tenant stores:

Field Purpose
PlanKey Stable key of the selected plan, such as starter or pro.
Features Tenant-level feature flag overrides stored as PostgreSQL jsonb.
Settings Tenant-level structured setting overrides stored as PostgreSQL jsonb.

Each plan stores:

Field Purpose
Key Stable plan identifier referenced by tenants.
Name Human-readable plan name.
Description Optional operator-facing description.
Features Plan default feature flags stored as PostgreSQL jsonb.
Settings Plan default structured settings stored as PostgreSQL jsonb.
IsActive Whether the plan can be assigned.
SortOrder Display ordering for future admin UI surfaces.
CreatedAt UTC creation timestamp.

The catalog migration creates a minimal starter plan before adding the tenant foreign key. This allows existing tenants to receive PlanKey = starter safely during migration. Full seed data for Starter and Pro is handled separately by the tenant-plan seeding work.

Startup seeding keeps the initial plans available and idempotently updates their defaults:

Plan key Name Intent
starter Starter Default plan for new tenants with conservative limits.
pro Pro Larger customer plan with higher limits and self-service registration.

Initial feature keys:

Feature Starter Pro
camps.enabled true true
branding.customLogo false true
registration.selfService false true

Initial settings:

Setting Starter Pro
limits.maxUsers 50 0
limits.maxCamps 3 25
registration.enabled false true
registration.requiresApproval true false
branding.theme default default

limits.maxUsers = 0 means unlimited users for the assigned plan. The system default limits.maxUsers = 5 remains a fallback only; it is not the default sold plan limit.

New tenants default to PlanKey = starter unless a later workflow explicitly allows a different plan to be supplied.

Effective Tenant Config

ITenantConfigResolver resolves the runtime configuration a tenant should receive. The resolver is registered in DI and can resolve by tenant id or tenant slug.

Effective config is built in this order:

SystemDefaults -> PlanDefaults -> TenantOverrides

Later layers override earlier layers.

The returned model contains:

Field Purpose
TenantId Catalog tenant identifier.
TenantSlug Stable tenant slug.
PlanKey Assigned plan key.
PlanName Assigned plan name.
Features Effective flat feature flag dictionary.
Settings Effective structured JSON settings object.

Feature merge rules:

  • feature dictionaries are flat;
  • plan defaults override system defaults by key;
  • tenant overrides override plan defaults by key;
  • missing keys do not remove earlier defaults.

Settings merge rules:

  • JSON objects are deep-merged;
  • scalar values replace earlier scalar or object values;
  • arrays replace earlier arrays and their contents are not merged;
  • type conflicts are resolved by replacement from the later layer;
  • empty dictionaries behave as empty layers;
  • JSON null values are preserved as explicit override values when supplied by the stored JSON model.

Failure behavior:

Condition Result error code
Tenant does not exist or is soft-deleted TENANT_NOT_FOUND
Assigned plan key does not resolve TENANT_PLAN_NOT_FOUND
Assigned plan is inactive TENANT_PLAN_INACTIVE

Tenant Config API

Tenant-facing clients can fetch effective config for the current tenant:

GET /api/v1/tenant/config
Authorization: Bearer <tenant-admin-token>
X-Tenant-Slug: acme

The route uses the tenant resolved from X-Tenant-Slug; the tenant id is not accepted in the URL for this endpoint.

In the portal, this route is exposed only to tenant admins at /tenant/config. Regular tenant users are redirected to /tenant/profile.

Platform administrators can inspect a tenant directly:

GET /api/admin/tenants/{tenantId}/config
Authorization: Bearer <organizor-admin-token>

Example response:

{
  "tenantId": "11111111-1111-1111-1111-111111111111",
  "tenantSlug": "acme",
  "planKey": "pro",
  "planName": "Pro",
  "features": {
    "camps.enabled": true,
    "branding.customLogo": true,
    "registration.selfService": true
  },
  "settings": {
    "limits": {
      "maxUsers": 0,
      "maxCamps": 25
    },
    "registration": {
      "enabled": true,
      "requiresApproval": false
    },
    "branding": {
      "theme": "default"
    }
  }
}

Expected error behavior:

Status Condition
401 Unauthorized Missing or invalid bearer token.
403 Forbidden Authenticated caller does not satisfy the endpoint policy or tenant access check.
400 Bad Request Tenant-scoped route is missing X-Tenant-Slug.
404 Not Found Tenant, assigned plan, or active plan cannot be resolved.

Manual verification:

  1. Seed starter and pro plans.
  2. Create or onboard a tenant assigned to pro.
  3. Add a tenant-level feature or setting override in the catalog.
  4. Call GET /api/v1/tenant/config with X-Tenant-Slug set to that tenant.
  5. Confirm the response contains system defaults, plan defaults, and tenant overrides with tenant overrides taking precedence.

Tenant User Self-Registration

Anonymous tenant-user registration is exposed through:

POST /api/public/register

The request body includes the tenant slug, username, email, and password. The endpoint does not use X-Tenant-Slug; tenant resolution for this operation comes from the submitted tenantSlug.

The registration workflow:

  1. Resolves the tenant by slug and requires it to be active.
  2. Resolves the tenant's effective config.
  3. Verifies self-service registration is enabled and the user limit is not exceeded.
  4. Creates an enabled Keycloak user.
  5. Assigns the user to /tenants/{slug}/users.

The portal /register page is a temporary shell for manual testing. Tenant-specific static websites are expected to provide their own branded registration UI later and call the same public API contract.

Tenant Config Management

Platform administrators can manage plan defaults and tenant-level overrides.

Plan endpoints:

GET /api/admin/tenant-plans
GET /api/admin/tenant-plans/{planKey}
PUT /api/admin/tenant-plans/{planKey}

Tenant override endpoints:

GET /api/admin/tenants/{tenantId}/config-overrides
PUT /api/admin/tenants/{tenantId}/config-overrides

Plan keys are immutable. A plan update can change name, description, feature defaults, settings defaults, active state, and sort order.

Tenant override updates can change:

  • assigned planKey;
  • tenant-level feature overrides;
  • tenant-level settings overrides.

Tenant override updates replace the full persisted override dictionaries. Omitted keys are removed from that tenant's overrides and inherited again from the assigned plan or system defaults.

Validation rules:

  • feature keys must be non-empty;
  • setting keys must be non-empty;
  • undefined JSON setting values are invalid;
  • assigned plan keys must resolve to active plans;
  • invalid config payloads return TENANT_CONFIG_INVALID;
  • missing tenants return TENANT_NOT_FOUND;
  • missing or inactive plans return TENANT_PLAN_NOT_FOUND or TENANT_PLAN_INACTIVE.

Portal surfaces:

  • /admin/plans lists and edits tenant plan defaults;
  • /admin/tenants exposes each tenant's effective config and tenant-level override editor through the Config action.

Manual verification:

  1. Open /admin/plans as an organizor-admin.
  2. Edit a plan feature default or setting default and save.
  3. Open /admin/tenants, choose a tenant assigned to that plan, and click Config.
  4. Confirm the effective config reflects the plan default change.
  5. Add a tenant feature or setting override and save.
  6. Confirm the effective preview refreshes and tenant override values take precedence.

Tenant Statuses

Status Meaning
Pending Tenant exists in the catalog but provisioning is not complete.
Active Tenant provisioning completed successfully.
Upgrading Reserved for upgrade lifecycle state.
Failed Provisioning failed or an unexpected onboarding error occurred.
Deleted Tenant has been soft-deleted.

Tenant Resolution

TenantResolutionMiddleware resolves tenant context for tenant-scoped routes.

It skips platform endpoints such as:

  • /api/admin;
  • /api/v1/tenants;
  • /health;
  • /scalar;
  • /openapi;
  • root and common static paths.

For tenant-scoped requests, clients must send:

X-Tenant-Slug: acme

The middleware loads the tenant from the catalog and stores TenantInfo in ITenantContext. If the header is missing, the response is 400 Bad Request. If the slug does not match a catalog tenant, the response is 404 Not Found.

Tenant Database Resolution

OrganizorDbContext uses a fallback in-memory database when no tenant has been resolved. This supports startup, Scalar, migrations, and design-time tooling.

When a tenant is resolved, PerTenantDbResolver loads the catalog tenant, builds a PostgreSQL connection string for that tenant database, and OrganizorDbContext uses that database.

Tenant Onboarding Flow

flowchart TD
    A[Onboard request] --> B[Create catalog tenant as Pending]
    B --> C[Store centralized website/auth settings]
    C --> D[Create Keycloak tenant groups]
    D --> E[Assign tenant roles to groups]
    E --> F[Create or update tenant public website client]
    F --> G[Create default tenant admin]
    G --> H[Create tenant database]
    H --> I[Apply tenant migrations]
    I --> J{Success?}
    J -->|Yes| K[Mark tenant Active]
    J -->|No| L[Mark tenant Failed]

The preferred full tenant creation route is POST /api/admin/tenants/onboard. It creates the catalog record, stores centralized website/auth settings, provisions Keycloak tenant access, creates the tenant database, applies migrations, and marks the tenant Active only after the workflow succeeds.

Onboarding accepts tenant website/auth settings for separate tenant UI projects:

Field Purpose
websiteBaseUrl Public tenant website base URL.
loginRedirectUris OIDC login callback URLs allowed by Keycloak.
logoutRedirectUris Post-logout redirect URLs allowed by Keycloak.
webOrigins Browser origins allowed by the Keycloak public client. Defaults to the website origin when omitted.
registrationRedirectUrl Optional tenant website URL used after registration flows.

These values are stored in tenant settings under website and auth, so Organizor remains the source of truth. Organizor also stores a generated auth.clientId using the format tenant-{slug}-web and provisions that Keycloak public client during onboarding.

The tenant public client is configured for Authorization Code Flow with PKCE, uses the configured login redirect URIs and web origins, stores the configured post-logout redirect URIs, and disables direct access grants, implicit flow, service accounts, and client authentication. Organizor also attaches a tenant-membership group mapper so tenant website tokens include the tenant claim used by API tenant authorization.

POST /api/v1/tenants creates only the catalog record with Pending status. It does not create Keycloak groups or a tenant database.

Hard deletion is intentionally guarded: the tenant must be soft-deleted before TenantLifecycleService runs the hard-delete workflow. That workflow removes the tenant Keycloak public client, removes the Keycloak tenant group and default admin user, drops the tenant database, and removes the catalog record.
