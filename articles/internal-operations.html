Internal Operations

This page documents internal routes and workflows for developers and operators.

Onboard Tenant

POST /api/admin/tenants/onboard
Authorization: Bearer <organizor-admin-token>
Content-Type: application/json

{
  "name": "Acme",
  "slug": "acme"
}

The onboarding flow:

  1. normalizes the slug to lowercase;
  2. creates a catalog tenant with Pending status;
  3. provisions Keycloak tenant groups under /tenants/{slug};
  4. assigns tenant-admin to /tenants/{slug}/admins and tenant-user to /tenants/{slug}/users;
  5. creates a default tenant admin user named {slug}-admin with a temporary password of ChangeMe123!;
  6. creates the tenant database using organizor_tenant_{slug};
  7. initializes PostgreSQL extensions;
  8. applies tenant migrations;
  9. marks the tenant Active on success or Failed on provisioning failure.

Example response:

{
  "id": "11111111-1111-1111-1111-111111111111",
  "name": "Acme",
  "slug": "acme",
  "databaseName": "organizor_tenant_acme",
  "createdAt": "2026-06-09T10:30:00Z",
  "status": "Active",
  "failureReason": null,
  "isDeleted": false
}

Query Tenants For Administration

GET /api/admin/tenants
Authorization: Bearer <organizor-admin-token>

Returns all tenant catalog records, including soft-deleted tenants. This differs from GET /api/v1/tenants, which returns only non-deleted records.

GET /api/admin/tenants/{id}
Authorization: Bearer <organizor-admin-token>

Returns one tenant by catalog ID, including soft-deleted records. These query endpoints are used by the portal tenant-management surface and are protected by the same RequireOrganizorAdminRole policy as lifecycle operations.

Example response:

{
  "id": "11111111-1111-1111-1111-111111111111",
  "name": "Acme",
  "slug": "acme",
  "databaseName": "organizor_tenant_acme",
  "createdAt": "2026-06-09T10:30:00Z",
  "status": "Active",
  "failureReason": null,
  "isDeleted": false
}

Tenant Config Administration

GET /api/admin/tenants/{id}/config
Authorization: Bearer <organizor-admin-token>

Returns the effective config for one tenant. Effective config is resolved from the tenant's assigned plan defaults plus any tenant-level overrides.

GET /api/admin/tenants/{id}/config-overrides
Authorization: Bearer <organizor-admin-token>

Returns only explicit tenant-level overrides.

PUT /api/admin/tenants/{id}/config-overrides
Authorization: Bearer <organizor-admin-token>
Content-Type: application/json

{
  "maxUsers": 25,
  "maxProjects": null,
  "allowAdvancedReporting": true
}

null clears an override and lets the tenant inherit the value from its plan. Override updates validate the resulting config before saving.

Tenant users can view their own effective config through the tenant-scoped endpoint:

GET /api/v1/tenant/config
Authorization: Bearer <tenant-token>
X-Tenant-Slug: acme

This endpoint requires tenant access and the RequireTenantUserRole policy.

Tenant Plan Administration

GET /api/admin/tenant-plans
Authorization: Bearer <organizor-admin-token>

Returns available tenant plans and their default feature settings.

PUT /api/admin/tenant-plans/{planKey}
Authorization: Bearer <organizor-admin-token>
Content-Type: application/json

{
  "maxUsers": 100,
  "maxProjects": 50,
  "allowAdvancedReporting": true
}

Plan updates validate the resulting default settings before saving. Existing tenant overrides remain intact, so tenants can continue to diverge from their plan where an override is set.

Upgrade Tenant

POST /api/admin/tenants/{id}/upgrade
Authorization: Bearer <organizor-admin-token>

Runs pending migrations for the tenant database.

Example response:

{
  "database": "organizor_tenant_acme",
  "success": true,
  "appliedMigrations": 2,
  "duration": "00:00:01.2340000",
  "error": null
}

Soft Delete Tenant

DELETE /api/admin/tenants/{id}
Authorization: Bearer <organizor-admin-token>
Content-Type: application/json

{
  "reason": "Customer cancellation"
}

Soft deletion marks the tenant as deleted, stores deletion metadata, and sets status to Deleted. The tenant database is not dropped.

Hard Delete Tenant

POST /api/admin/tenants/{id}/hard-delete
Authorization: Bearer <organizor-admin-token>

Hard deletion requires the tenant to already be soft-deleted. It:

  1. deletes the default Keycloak admin user named {slug}-admin when it exists;
  2. deletes the Keycloak tenant group /tenants/{slug} when it exists;
  3. drops the tenant database;
  4. removes the catalog record.

Keycloak cleanup tolerates missing groups or users so a partially-provisioned tenant can still be cleaned up.

Portal Admin Tenant Control

The Blazor portal exposes the tenant operations above through /admin/tenants for users with the organizor-admin role.

The page uses AdminTenantService, which calls the same admin endpoints documented in this article. Operators can:

  • view all tenants, including soft-deleted tenants;
  • filter the catalog by name, slug, database, or status;
  • onboard a new tenant;
  • inspect effective tenant config;
  • edit tenant config overrides;
  • manage plan default settings from /admin/plans;
  • run a tenant upgrade;
  • soft-delete a tenant with a reason;
  • hard-delete a tenant after it has been soft-deleted.

The portal does not bypass API authorization. Each operation still requires a bearer token accepted by RequireOrganizorAdminRole.

Scheduled Tenant Jobs

Organizor is wired for Quartz recurring background work, but tenant job scheduling is not currently enabled on startup. Program.cs contains a commented-out scheduling block for future use.

The scheduler:

  1. loads all tenants from the catalog database;
  2. creates a durable SyncTenantJob with job key sync-{tenantId} in the tenant-jobs group;
  3. stores TenantId and TenantSlug in the Quartz job data map;
  4. creates a trigger named sync-{tenantId}-trigger in the tenant-triggers group;
  5. schedules the job when it is new, or replaces and reschedules it when it already exists.

Current trigger cadence:

0/10 * * * * ?

That Quartz cron expression would run the tenant synchronization job every 10 seconds when scheduling is enabled.

SyncTenantJob reads the tenant data from the job data map, sets ITenantContext, and then runs tenant-scoped work through OrganizorDbContext. The current implementation logs execution and contains placeholder synchronization work.

Quartz persistence is stored in the catalog database and uses the PostgreSQL tables added by the AddQuartzTables migration. The API configures Quartz with the Catalog connection string, JSON serialization, and clustering enabled.

Documentation Deployment

The repository contains a GitHub Actions workflow at .github/workflows/docfx-deploy.yml.

On pushes to master, it:

  1. checks out this repository;
  2. installs DocFX;
  3. builds docs/docfx.json;
  4. checks out the public documentation repository;
  5. copies docs/_site into that repository;
  6. commits and pushes the generated documentation.

The workflow uses the DOCS_DEPLOY_KEY secret to push to the public docs repository.

Sitemap and Crawlers

DocFX generates docs/_site/sitemap.xml from the build.sitemap.baseUrl value in docs/docfx.json.

The documentation source includes robots.txt, which is copied into the generated site and points crawlers to the sitemap.
