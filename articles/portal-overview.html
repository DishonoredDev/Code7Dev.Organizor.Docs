Portal UI Overview

The Portal UI is the Blazor WebAssembly front end for Organizor. It handles Keycloak sign-in, role-based routing, platform administration, tenant administration, public registration testing, and authenticated API calls to the backend.

This page reflects the issue 98 portal work completed after the last documentation update.

Current Capabilities

The portal currently supports:

  • Keycloak OIDC login with the organizor-ui client.
  • Role extraction from Keycloak realm roles and organizor-ui client roles.
  • Automatic role-based routing after login.
  • Separate admin and tenant shells.
  • An admin dashboard route at /admin.
  • Tenant administration at /admin/tenants for platform administrators.
  • Tenant plan default management at /admin/plans.
  • Tenant user management from active tenant rows for platform administrators.
  • Tenant effective config inspection and override editing from /admin/tenants.
  • Tenant-scoped user management at /tenant/users for tenant administrators.
  • Tenant effective config at /tenant/config for tenant administrators.
  • Tenant profile at /tenant/profile for tenant administrators and tenant users.
  • Temporary public registration shell at /register for testing tenant-user self-registration.
  • Logout through /logout or the shared logout button.
  • Current-user display with username, email, display name, tenant claim, roles, Keycloak groups, and tenant website navigation when available.
  • Tenant dashboard placeholder under /tenant.

The /admin/tenants, /admin/plans, /admin/users, /tenant/users, /tenant/config, and /register pages are backed by real API routes. The /register page is intentionally a temporary shell for exercising the public registration endpoint until tenant-specific static websites provide their own registration UI.

Technology Stack

  • Blazor WebAssembly for client-side rendering.
  • .NET 10 for the portal project.
  • Keycloak for authentication using OIDC Authorization Code Flow with PKCE.
  • Radzen.Blazor for the admin tenant grid, cards, forms, buttons, badges, alerts, and notifications.
  • IHttpClientFactory plus a custom AuthorizationMessageHandler for API calls.

RoleRedirector is mounted globally in App.razor, but it only redirects from the neutral entry routes (/ and the login callback). It sends organizor-admin users to /admin, tenant-admin users to /tenant, and tenant-user users to /tenant/profile. It must not redirect when the user is already on a target area, otherwise the portal can reload-loop.

Admin Tenant Management

The admin tenant page uses Radzen components and the AdminTenantService client. It supports:

  • loading all tenants including soft-deleted tenants;
  • filtering tenants by name, slug, database name, or status;
  • viewing active, deleted, and failed tenant counts;
  • onboarding a tenant with name, slug, website base URL, login redirect URL, logout redirect URL, web origin, and optional registration redirect validation;
  • upgrading a tenant database by running pending migrations;
  • soft-deleting a tenant with an operator reason;
  • hard-deleting a previously soft-deleted tenant.
  • opening user management for active tenants.
  • inspecting effective tenant config;
  • editing tenant plan assignment and tenant-level overrides.

The page calls these backend endpoints:

UI action API endpoint
Load tenants GET /api/admin/tenants
Load one tenant GET /api/admin/tenants/{id}
Onboard tenant POST /api/admin/tenants/onboard
Upgrade tenant POST /api/admin/tenants/{id}/upgrade
Inspect effective config GET /api/admin/tenants/{id}/config
Load tenant overrides GET /api/admin/tenants/{id}/config-overrides
Save tenant overrides PUT /api/admin/tenants/{id}/config-overrides
Soft delete tenant DELETE /api/admin/tenants/{id}
Hard delete tenant POST /api/admin/tenants/{id}/hard-delete

All admin tenant operations require a valid bearer token with the organizor-admin role.

Tenant onboarding stores website/auth settings in centralized tenant config so later tenant website and auth provisioning can use Organizor as the source of truth.

Admin Plan Management

The admin plans page uses AdminTenantService and supports:

  • loading tenant plan definitions;
  • editing plan name, description, active state, sort order, feature defaults, and settings defaults;
  • saving plan changes through the admin plan API.

The page calls these backend endpoints:

UI action API endpoint
Load plans GET /api/admin/tenant-plans
Save plan defaults PUT /api/admin/tenant-plans/{planKey}

Plan keys are intentionally immutable.

Admin User Management

The tenant catalog page is the entry point for platform tenant-user management. Platform administrators open users from an active tenant row, which navigates to /admin/users?tenantId={id}. The admin users page manages only that tenant's Keycloak users. It can create users, list users, toggle enabled state, delete users, and assign tenant roles within the selected tenant.

The admin sidebar does not expose /admin/users as a standalone global directory. /admin/users without a valid active tenant id redirects to /admin/tenants. The page calls the admin user-management API through AdminTenantService. All operations require organizor-admin.

Tenant User Management

Tenant administrators can open /tenant/users to manage users for their own tenant. The page uses the tenant claim from the authenticated user; ApiAuthorizationMessageHandler adds X-Tenant-Slug to tenant-scoped requests.

Regular tenant-user accounts do not see the tenant user-management route.

Tenant Config Page

Tenant admins can open /tenant/config. The page calls GET /api/v1/tenant/config through TenantConfigService. ApiAuthorizationMessageHandler adds X-Tenant-Slug from the authenticated user's tenant claim.

Regular tenant-user accounts should not see tenant configuration in the portal. Their default redirect target is /tenant/profile.

Tenant Profile Page

Tenant admins and regular tenant users can open /tenant/profile. The page shows read-only Keycloak-backed identity data: display name, email, username, tenant, roles, and groups.

Tenant configuration was intentionally removed from the profile page. The password-change action starts the controlled backend flow. Profile update allows only first name and last name edits. Security options remain a disabled placeholder.

The account-action strategy is Organizor-mediated and Keycloak-completed. Password-change initiation uses POST /api/v1/tenant/account-actions/change-password, which passes through Organizor authorization and tenant-access checks before setting Keycloak UPDATE_PASSWORD for the authenticated user. After the action starts, the portal tells the user to sign out and sign in again to complete the Keycloak password update. The portal does not collect new passwords and does not expose a direct Keycloak account-console link to regular tenant users or tenant admins.

Profile update uses PUT /api/v1/tenant/account-actions/profile, which passes through the same current-user tenant checks and writes only Keycloak firstName and lastName. The portal does not expose username, email, role, group, tenant membership, credential, enabled-state, required-action, or arbitrary-attribute editing from the current-user profile page.

Public Registration Shell

The /register page is a temporary public shell for exercising tenant-user self-registration. It posts to POST /api/public/register through PublicRegistrationService.

The long-term model is that tenant-specific static websites own their registration UI and call the public API contract directly. This keeps tenant branding and UX independent from the Organizor portal.

Tenant rows expose the catalog and lifecycle fields used by the UI:

Field Use
id Action target for upgrade and delete calls.
name, slug, databaseName Catalog display and search.
createdAt Created timestamp shown in local time.
status Lifecycle state used for badges and failed counts.
failureReason Failure detail shown below the tenant name when present.
isDeleted Controls deleted badge state and whether hard delete is available.

Authentication Flow

The Portal UI uses:

  • OIDC Authorization Code Flow with PKCE;
  • Keycloak as the identity provider;
  • access tokens for API calls;
  • Blazor AuthenticationState for role and user context;
  • KeycloakClaimsPrincipalFactory to promote Keycloak roles into Blazor role claims.
  • tenant group-membership claims emitted by the organizor-ui client mapper created during tenant onboarding.

Current local configuration:

Setting Value
Portal origin https://localhost:7025
Keycloak authority https://localhost:8443/realms/organizor-dev
Keycloak client organizor-ui
Login callback https://localhost:7025/authentication/login-callback
Logout callback https://localhost:7025/
API base URL https://localhost:7184

The API Keycloak:Authority must match the token issuer exactly. A portal token issued by https://localhost:8443/realms/organizor-dev will fail API validation if the API is configured for http://localhost:8443/realms/organizor-dev.

API Integration

The portal uses a named HttpClient called api with base address https://localhost:7184 for authenticated calls. It uses public-api for anonymous public contract calls such as resolving the current tenant website link.

ApiAuthorizationMessageHandler:

  • configures the authorized API URL;
  • requests the OIDC scopes used by the portal;
  • attaches bearer tokens to API requests;
  • adds X-Tenant-Slug when UserContextService can resolve a tenant claim.

CurrentUserPanel resolves the authenticated user's tenant website through GET /api/public/tenants/{slug}/auth and shows Back to Website only when the returned contract contains a website URL.

The handler is attached with .AddHttpMessageHandler<ApiAuthorizationMessageHandler>() and configured once in its constructor. Do not configure the same AuthorizationMessageHandler instance more than once; Blazor will throw a handler already configured error.

Summary

The portal now supports tenant lifecycle operations, tenant plan defaults, tenant-level config overrides, platform tenant-user management, tenant-admin user management, tenant-admin config inspection, tenant profile display, and public registration testing.
