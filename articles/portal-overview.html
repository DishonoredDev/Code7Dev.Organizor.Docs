Portal UI Overview

The Portal UI is the Blazor WebAssembly front end for Organizor. It handles Keycloak sign-in, role-based routing, tenant administration, and authenticated API calls to the backend.

This page reflects the issue 98 portal work completed after the last documentation update.

Current Capabilities

The portal currently supports:

  • Keycloak OIDC login with the organizor-ui client.
  • Role extraction from Keycloak realm roles and organizor-ui client roles.
  • Automatic role-based routing after login.
  • Separate admin and tenant shells.
  • An admin dashboard route at /admin.
  • Tenant administration at /admin/tenants for platform administrators.
  • Logout through /logout or the shared logout button.
  • Current-user display with username, email, tenant claim, and Keycloak groups.
  • Tenant dashboard/profile placeholders under /tenant.

The /admin/tenants page is backed by real API routes under /api/admin/tenants. It is not mock UI. Tenant-facing feature routes are still placeholders.

Technology Stack

  • Blazor WebAssembly for client-side rendering.
  • .NET 10 for the portal project.
  • Keycloak for authentication using OIDC Authorization Code Flow with PKCE.
  • Radzen.Blazor for the admin tenant grid, cards, forms, buttons, badges, alerts, and notifications.
  • IHttpClientFactory plus a custom AuthorizationMessageHandler for API calls.

Routes and Layouts

Route Layout Required role Purpose
/ MainLayout none Entry page. Authenticated users are redirected by role.
/admin AdminLayout organizor-admin Admin dashboard placeholder.
/admin/tenants AdminLayout organizor-admin Tenant catalog and lifecycle management.
/tenant TenantLayout tenant-admin Tenant dashboard placeholder.
/tenant/profile TenantLayout tenant-admin Tenant profile placeholder.
/logout none authenticated user Redirects to the Blazor OIDC logout endpoint and returns to /.
/authentication/* authentication page none Blazor WebAssembly OIDC endpoints.

The admin shell currently contains a navigation link for /admin/users, and the tenant shell contains a navigation link for /tenant/camps. Those are navigation placeholders only; this branch does not add backing Razor pages for those routes.

RoleRedirector is mounted globally in App.razor, but it only redirects from the neutral entry routes (/ and the login callback). It must not redirect when the user is already on /admin or /tenant, otherwise the portal can reload-loop.

Admin Tenant Management

The admin tenant page uses Radzen components and the AdminTenantService client. It supports:

  • loading all tenants including soft-deleted tenants;
  • filtering tenants by name, slug, database name, or status;
  • viewing active, deleted, and failed tenant counts;
  • onboarding a tenant with name and slug validation;
  • upgrading a tenant database by running pending migrations;
  • soft-deleting a tenant with an operator reason;
  • hard-deleting a previously soft-deleted tenant.

The page calls these backend endpoints:

UI action API endpoint
Load tenants GET /api/admin/tenants
Load one tenant GET /api/admin/tenants/{id}
Onboard tenant POST /api/admin/tenants/onboard
Upgrade tenant POST /api/admin/tenants/{id}/upgrade
Soft delete tenant DELETE /api/admin/tenants/{id}
Hard delete tenant POST /api/admin/tenants/{id}/hard-delete

All admin tenant operations require a valid bearer token with the organizor-admin role.

Tenant rows expose the catalog and lifecycle fields used by the UI:

Field Use
id Action target for upgrade and delete calls.
name, slug, databaseName Catalog display and search.
createdAt Created timestamp shown in local time.
status Lifecycle state used for badges and failed counts.
failureReason Failure detail shown below the tenant name when present.
isDeleted Controls deleted badge state and whether hard delete is available.

Authentication Flow

The Portal UI uses:

  • OIDC Authorization Code Flow with PKCE;
  • Keycloak as the identity provider;
  • access tokens for API calls;
  • Blazor AuthenticationState for role and user context;
  • KeycloakClaimsPrincipalFactory to promote Keycloak roles into Blazor role claims.

Current local configuration:

Setting Value
Portal origin https://localhost:7025
Keycloak authority https://localhost:8443/realms/organizor-dev
Keycloak client organizor-ui
Login callback https://localhost:7025/authentication/login-callback
Logout callback https://localhost:7025/
API base URL https://localhost:7184

The API Keycloak:Authority must match the token issuer exactly. A portal token issued by https://localhost:8443/realms/organizor-dev will fail API validation if the API is configured for http://localhost:8443/realms/organizor-dev.

API Integration

The portal uses a named HttpClient called api with base address https://localhost:7184.

ApiAuthorizationMessageHandler:

  • configures the authorized API URL;
  • requests the OIDC scopes used by the portal;
  • attaches bearer tokens to API requests;
  • adds X-Tenant-Slug when UserContextService can resolve a tenant claim.

The handler is attached with .AddHttpMessageHandler<ApiAuthorizationMessageHandler>() and configured once in its constructor. Do not configure the same AuthorizationMessageHandler instance more than once; Blazor will throw a handler already configured error.

Summary

Issue 98 moved the portal from a basic authenticated shell toward an operational admin portal. The most complete workflow today is tenant control under /admin/tenants; user management and tenant feature pages are still placeholders until backing API use cases are added.
