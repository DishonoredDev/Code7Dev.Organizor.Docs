Tenant Config Model

Tenant configuration is catalog-owned. It combines system defaults, plan defaults, and tenant overrides into one effective config model.

Important

This page describes the legacy effective-configuration layer. It does not decide which product modules a tenant can use. Module deployment, plan entitlement, and tenant installation are separately managed through the Tenant Modules model.

Plans And Overrides

Tenant plans are persisted in the catalog database through the tenant_plans table. A plan defines default feature flags and structured settings for tenants assigned to that plan.

Each tenant stores the following compatibility configuration:

Field Purpose
PlanKey Stable key of the selected plan, such as starter or pro.
Features Tenant-level legacy feature flag overrides stored as PostgreSQL jsonb. It is not module entitlement.
Settings Tenant-level structured setting overrides stored as PostgreSQL jsonb. It is not module installation state.

Each plan stores:

Field Purpose
Key Stable plan identifier referenced by tenants.
Name Human-readable plan name.
Description Optional operator-facing description.
Features Plan default legacy feature flags stored as PostgreSQL jsonb. It is not module entitlement.
Settings Plan default structured settings stored as PostgreSQL jsonb. It is not module configuration unless an owning typed contract validates it.
IsActive Whether the plan can be assigned.
SortOrder Display ordering for future admin UI surfaces.

Startup seeding keeps the initial plans available. It creates missing plan definitions but does not overwrite existing operator-managed plan metadata, legacy configuration, or module entitlements:

Plan key Intent
starter Default plan for new tenants with conservative limits.
pro Larger customer plan with higher limits and self-service registration.

limits.maxUsers = 0 means unlimited users for the assigned plan. The system default limits.maxUsers = 5 remains a fallback only.

The starter and pro plans also have separate module bundles. The starter plan includes activities and offers the other initial modules as add-ons; pro includes the full family-activity bundle. See Tenant Modules.

Effective Config

ITenantConfigResolver resolves runtime config by tenant id or tenant slug.

Effective config is built in this order:

SystemDefaults -> PlanDefaults -> TenantOverrides

Later layers override earlier layers.

The returned model contains:

Field Purpose
TenantId Catalog tenant identifier.
TenantSlug Stable tenant slug.
PlanKey Assigned plan key.
PlanName Assigned plan name.
Features Effective flat feature flag dictionary.
Settings Effective structured JSON settings object.

Legacy feature merge rules:

  • feature dictionaries are flat;
  • plan defaults override system defaults by key;
  • tenant overrides override plan defaults by key;
  • missing keys do not remove earlier defaults.

Settings merge rules:

  • JSON objects are deep-merged;
  • scalar values replace earlier scalar or object values;
  • arrays replace earlier arrays;
  • type conflicts are replaced by the later layer;
  • JSON null values are preserved as explicit override values.

Failure behavior:

Condition Result error code
Tenant does not exist or is soft-deleted TENANT_NOT_FOUND
Assigned plan key does not resolve TENANT_PLAN_NOT_FOUND
Assigned plan is inactive TENANT_PLAN_INACTIVE

Tenant Config API

Tenant admins fetch effective config for their current tenant:

GET /api/v1/tenant/config
Authorization: Bearer <tenant-admin-token>
X-Tenant-Slug: acme

Platform administrators inspect a tenant directly:

GET /api/admin/tenants/{tenantId}/config
Authorization: Bearer <organizor-admin-token>

See Tenant Config Operations for platform admin update endpoints.
