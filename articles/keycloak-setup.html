Keycloak Setup

This document describes the Keycloak configuration for the Organizor development environment. It includes realm setup, API/UI clients, tenant groups, claim mapping, user/role setup, and the admin-client permissions used by tenant onboarding.

The local Keycloak container is expected to run over HTTPS at https://localhost:8443. See Keycloak HTTPS Setup before configuring clients.

On first startup with an empty Keycloak database, Docker Compose imports docker/keycloak/import/organizor-dev-realm.json. This creates the organizor-dev realm, the three development clients, realm roles, the /tenants root group, and service-account permissions for backend provisioning. Client secrets are generated by Keycloak and must be copied into local user secrets or local HTTP-client environment files as needed.

Normal docker compose up -d reuse does not re-import the realm and does not regenerate client secrets. docker compose down -v deletes the local Keycloak database volume; the next startup imports the realm again and generates new client secrets. After using down -v, copy the new organizor-admin client secret into API user secrets:

dotnet user-secrets set "Keycloak:AdminClientSecret" "<client-secret>" --project .\Code7Dev.Organizor.Api\Code7Dev.Organizor.Api.csproj

Realm Setup

  • Open Keycloak Admin Console.
  • Realm dropdown -> Create Realm.
  • Name: organizor-dev.
  • Save.

API Client (organizor-api)

Settings:

  • Client type: OpenID Connect
  • Client ID: organizor-api
  • Name: Organizor API

Required values:

  • Client authentication: ON
  • Authorization: OFF
  • Standard flow: OFF
  • Direct access grants: ON
  • Implicit flow: OFF
  • Service accounts roles: ON

Credentials:

  • Open the Credentials tab.
  • Copy the Client Secret.
  • Store it in development tooling that requests tokens.

The API currently validates bearer tokens only; it does not read the client secret from application configuration. The client secret is only needed by tooling or services that request tokens with the client_credentials flow.

The infrastructure Keycloak admin client uses the separate organizor-admin service-account client during tenant onboarding. Configure these application settings from that client:

{
  "Keycloak": {
    "Authority": "https://localhost:8443/realms/organizor-dev",
    "BaseUrl": "https://localhost:8443",
    "Realm": "organizor-dev",
    "AdminClientId": "organizor-admin",
    "AdminClientSecret": "<client-secret>"
  }
}

For tenant onboarding and hard deletion, the organizor-admin service account must be allowed to use the Keycloak Admin REST API. The development realm import assigns the required realm-management client roles for:

  • reading groups and users;
  • creating and deleting tenant groups;
  • assigning realm roles to groups;
  • creating the default tenant admin user;
  • resetting the default tenant admin password;
  • adding users to groups;
  • deleting the default tenant admin user during hard deletion;
  • reading, creating, updating, and deleting clients for per-tenant static website clients.

UI Client (organizor-ui)

Settings:

  • Client type: OpenID Connect
  • Client ID: organizor-ui
  • Name: Organizor UI

Required values:

  • Client authentication: OFF
  • Authorization: OFF
  • Standard flow: ON
  • Direct access grants: OFF
  • Implicit flow: OFF
  • Service accounts roles: OFF

Development redirect URIs:

  • https://localhost:7025/*
  • https://localhost:7025/authentication/login-callback
  • http://localhost:5080/*

Web origins:

  • https://localhost:7025
  • http://localhost:5080

Use * only for quick local testing. Explicit origins are preferable because they catch redirect and CORS mistakes earlier.

Tenant onboarding must not mutate the central organizor-ui portal client. Static tenant websites receive their own generated public client instead, using tenant-{slug}-web as the client ID.

Tenant Website Clients

POST /api/admin/tenants/onboard creates or updates a tenant-specific public client for the tenant website.

Client shape:

  • Client ID: tenant-{slug}-web
  • Client authentication: OFF
  • Standard flow: ON
  • PKCE method: S256
  • Direct access grants: OFF
  • Implicit flow: OFF
  • Service accounts: OFF
  • Redirect URIs: onboarding loginRedirectUris
  • Web origins: onboarding webOrigins, or website origin when omitted
  • Post-logout redirect URIs: onboarding logoutRedirectUris
  • Protocol mapper: tenant-membership
  • Mapper type: Group Membership
  • Token claim name: tenant
  • Full group path: ON
  • Add to access token, ID token, and userinfo: ON

During hard deletion, Organizor deletes this tenant website client.

Static websites can discover their public auth contract at:

GET /api/public/tenants/{slug}/auth

The response includes the Keycloak authority, generated client id, PKCE flag, required scopes, tenant header name, tenant claim name, expected tenant roles, expected tenant group paths, redirect metadata, and public registration endpoint.

Tenant Groups

Tenant onboarding creates the group structure automatically when POST /api/admin/tenants/onboard is used. Manual setup is only needed for bootstrap or testing.

Group structure:

  • /tenants
  • /tenants/acme
  • /tenants/acme/users
  • /tenants/acme/admins

Each tenant has:

  • /users group
  • /admins group

On onboarding, Organizor assigns:

  • tenant-admin to /tenants/{slug}/admins;
  • tenant-user to /tenants/{slug}/users.

It also creates a default tenant admin user:

  • Username: {slug}-admin
  • Email: {slug}-admin@organizor.local
  • Temporary password: generated during onboarding unless Keycloak:DefaultTenantAdminTemporaryPassword is configured
  • Group: /tenants/{slug}/admins

During hard deletion, Organizor removes the tenant website client, removes the tenant group /tenants/{slug}, and deletes the default {slug}-admin user when it exists.

Tenant Membership Claim Mapper

Generated tenant website clients receive this mapper automatically during onboarding.

Location:

  • Clients -> organizor-api
  • Client scopes -> organizor-api-dedicated
  • Mappers -> Create

Values:

  • Name: tenant-membership
  • Mapper type: Group Membership
  • Token Claim Name: tenant
  • Full group path: ON
  • Add to ID token: ON
  • Add to access token: ON
  • Add to userinfo: ON

User Setup

Create these realm roles before assigning users:

  • organizor-admin
  • tenant-admin
  • tenant-user

Platform admin:

  • Username: admin@organizor.dev
  • Password: local development password stored outside git
  • Assign realm role: organizor-admin
  • No tenant groups assigned

Tenant admin:

  • Username: admin@acme.dev
  • Password: local development password stored outside git
  • Assign realm role: tenant-admin
  • Assign group: /tenants/acme/admins

Tenant user:

  • Username: user@acme.dev
  • Password: local development password stored outside git
  • Assign realm role: tenant-user
  • Assign group: /tenants/acme/users

Token Testing

Token endpoint:

  • https://localhost:8443/realms/organizor-dev/protocol/openid-connect/token

Expected role claim examples:

{
  "realm_access": {
    "roles": ["organizor-admin"]
  },
  "resource_access": {
    "organizor-api": {
      "roles": ["tenant-user"]
    }
  }
}

Example tenant claim:

"tenant": ["/tenants/acme/admins"]
