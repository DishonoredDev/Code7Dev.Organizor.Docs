Tenant Lifecycle Operations

All endpoints on this page require a token issued by the configured platform realm with the organizor-admin role. A tenant-realm role with the same text cannot access these operations.

The platform administrator uses one control-plane login. The API uses its backend-only organizor-provisioner service account in Keycloak master to carry out realm lifecycle operations; no tenant or platform browser receives that secret.

Onboard Tenant

POST /api/admin/tenants/onboard
Authorization: Bearer <platform-organizor-admin-token>
Content-Type: application/json

{
  "name": "Acme",
  "slug": "acme",
  "tenantAdminPortalBaseUrl": "https://admin.acme.example.com",
  "authSettings": {
    "websiteBaseUrl": "https://acme.example.com",
    "loginRedirectUris": ["https://acme.example.com/authentication/login-callback"],
    "logoutRedirectUris": ["https://acme.example.com"],
    "webOrigins": ["https://acme.example.com"],
    "registrationRedirectUrl": "https://acme.example.com/register/complete"
  }
}

The onboarding flow normalizes the slug, assigns immutable catalog realm tenant-acme, validates tenant website/auth and tenant-admin portal URLs, stores centralized auth settings plus the unique catalog portal URL, creates the catalog tenant as Pending, provisions the tenant Keycloak realm, creates the tenant database, applies tenant migrations, and marks the tenant Active on success.

Realm provisioning creates realm-local tenant-admin and tenant-user roles, /admins and /users groups, an organizor-api audience client, separate tenant website and tenant-admin portal clients, and the default tenant administrator. The website and portal public auth contracts then return https://<keycloak>/realms/tenant-acme, not the platform realm.

URL validation rejects wildcards, requires absolute HTTPS URLs, and allows HTTP only for local development hosts such as localhost and 127.0.0.1. Web origins must be origins only.

Query Tenants

GET /api/admin/tenants
Authorization: Bearer <platform-organizor-admin-token>

Returns all tenant catalog records, including soft-deleted tenants.

GET /api/admin/tenants/{id}
Authorization: Bearer <platform-organizor-admin-token>

Returns one tenant by catalog ID, including soft-deleted records. The catalog-owned identity realm is an internal immutable lifecycle mapping, not editable tenant configuration.

Upgrade Tenant

POST /api/admin/tenants/{id}/upgrade
Authorization: Bearer <platform-organizor-admin-token>

Runs pending migrations for the tenant database.

Example response:

{
  "database": "organizor_tenant_acme",
  "success": true,
  "appliedMigrations": 2,
  "duration": "00:00:01.2340000",
  "error": null
}

Soft Delete Tenant

DELETE /api/admin/tenants/{id}
Authorization: Bearer <platform-organizor-admin-token>
Content-Type: application/json

{
  "reason": "Customer cancellation"
}

Soft deletion first disables the tenant's complete Keycloak realm. Only after that succeeds does Organizor mark the catalog tenant as deleted, store deletion metadata, and set status to Deleted. The tenant database is not dropped.

If Keycloak cannot disable the realm, the catalog tenant remains undeleted and the operation returns TENANT_IDENTITY_PROVIDER_FAILED. A soft-deleted tenant is removed from the API issuer allow-list, so an already-issued token from its realm is rejected immediately.

Hard Delete Tenant

POST /api/admin/tenants/{id}/hard-delete
Authorization: Bearer <platform-organizor-admin-token>

Hard deletion requires the tenant to already be soft-deleted. It performs cleanup in this order:

  1. Delete the complete tenant realm, including users, sessions, groups, roles, website clients, and API audience client.
  2. Drop the tenant database.
  3. Remove the catalog record.

A missing tenant realm is treated as already deleted, allowing retry of a partially completed cleanup. If realm deletion fails, the API returns TENANT_IDENTITY_PROVIDER_FAILED and does not drop the database or remove the catalog record.
