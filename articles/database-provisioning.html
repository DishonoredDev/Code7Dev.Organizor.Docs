Database Provisioning

Organizor uses one catalog database and one PostgreSQL database per tenant.

Catalog Database

CatalogDbContext stores tenant records in the tenants table and tenant plan definitions in the tenant_plans table.

Important constraints:

Field Constraint
Name Required, max length 200.
Slug Required, max length 100, unique index.
DatabaseName Required, max length 200.
PlanKey Required, max length 100, defaults to starter, references tenant_plans.key.
Features Required PostgreSQL jsonb, defaults to {}.
Settings Required PostgreSQL jsonb, defaults to {}.
IsDeleted Required, defaults to false.
DeletionReason Optional, max length 500.

Important tenant_plans constraints:

Field Constraint
Key Required, max length 100, primary key.
Name Required, max length 200.
Description Optional, max length 500.
Features Required PostgreSQL jsonb, defaults to {}.
Settings Required PostgreSQL jsonb, defaults to {}.
IsActive Required, defaults to true.
SortOrder Required, defaults to 0.
CreatedAt Required UTC timestamp.

The tenant-config migration inserts a minimal starter plan row before adding the tenant plan foreign key. This keeps existing tenants migratable because their new PlanKey defaults to starter.

After migrations are applied, startup seeding idempotently creates or updates the initial tenant plans:

Plan key Purpose
starter Default plan for new tenants with conservative limits.
pro Larger customer plan with higher limits and more enabled features.

The seed data is managed in SeedCatalogDbAsync. It runs after CatalogDbContext migrations so it can enrich the minimal migration-created starter row and add pro.

Manual verification after startup:

select key, name, features, settings
from tenant_plans
where key in ('starter', 'pro')
order by sort_order;

Creating or onboarding a tenant without explicit plan selection should leave tenants.plan_key set to starter.

On startup, the API checks whether the catalog database exists, creates it when needed, and applies catalog migrations.

The full tenant onboarding workflow is documented in Internal Operations. Database provisioning is one part of that workflow; the catalog-owned tenant Keycloak realm and its realm-local identity resources are provisioned before the tenant database is created.

Tenant Database Naming

Tenant databases use:

organizor_tenant_{slug}

Example:

organizor_tenant_acme

Slugs are normalized to lowercase before tenant records are written.

PostgreSQL Requirements

The configured PostgreSQL user must be able to:

  • connect to the admin postgres database;
  • create tenant databases;
  • drop tenant databases during hard deletion;
  • create extensions in tenant databases.

Tenant database creation currently uses:

CREATE DATABASE "{databaseName}" OWNER = postgres ENCODING = 'UTF8';

Each tenant database is initialized with:

CREATE EXTENSION IF NOT EXISTS "pgcrypto";
CREATE EXTENSION IF NOT EXISTS "citext";

Hard deletion uses:

DROP DATABASE IF EXISTS "{databaseName}" WITH (FORCE);

Migration Flow

TenantMigrator builds a tenant-specific connection string, checks pending migrations on OrganizorDbContext, applies them, and returns:

Field Meaning
Database Tenant database name.
Success Whether migrations completed.
AppliedMigrations Count of migrations pending before execution.
Duration Migration runtime.
Error Error message when migration fails.

The active tenant migrations currently create only implemented tenant-business tables. As of tenant person relationships, that means:

Table Purpose
organizations Tenant-local organization records managed from the portal.
activity_types Tenant-local activity type definitions managed from the portal.
activity_type_document_capabilities Activity-type document capability assignments and capability-specific options.
activity_type_registration_fields Registration field metadata attached to activity types.
activities Tenant-local activity records with optional organization references.
people Minimal participant person records required by registration submission.
registrations Activity registration records and manual payment state.
person_relationships Tenant-local directional relationships from a responsible/contact person to a child or related person.
email_templates Tenant-local configurable email templates keyed by mail purpose and scope.
email_deliveries Tenant-local email delivery attempt log keyed by mail purpose.

Organization membership tables are intentionally excluded until their owning feature specs are implemented and their migrations are added.

Onboarding and Cleanup

During POST /api/admin/tenants/onboard, the database steps are:

  1. create the tenant database named organizor_tenant_{slug};
  2. initialize required PostgreSQL extensions;
  3. apply pending OrganizorDbContext migrations;
  4. return success so the tenant can be marked Active.

If the migration result fails or onboarding throws unexpectedly, the catalog tenant is marked Failed.

During hard deletion, the tenant must already be soft-deleted. The hard-delete workflow deletes the complete tenant realm first, drops the tenant database with DROP DATABASE IF EXISTS ... WITH (FORCE), and then removes the catalog record. Realm deletion failure stops the database/catalog cleanup.
